Event Management is a microservice that is installed and run just like any other microservice. Its full name is Alkami.MicroServices.EventManagement.Service.Host.

- The Event Management microservice is deployed as part of the Event Management compound.
- Event Management is a microservice that is extended by other smaller microservices called processors. An example of an Event Management processor is the Security Alerts Processor.
- When creating new processors for Event Management to use, you can use the Event Management Visual Studio Processor Templates (similar to the Alkami MicroService Visual Studio Templates).
- Processors are defined as specific types: TriggerCustomEvents, CronBased and Event Based.The difference between TriggerCustomEvents and Event Based are that the latter are triggered based on well-defined events found in Broker. As of Oct. 2nd, 2018, no well-defined Event Based processors have been created.
#### What does Event Management Do?

The primary purpose of Event Management is receiving events and asynchronously matching those events to the various services that handle those events. Some events will have no processors that need to respond to them for an FI, while others may have multiple processors that all need to be sent the event. Event management allows services (referred to as Event Processors, or just Processors) to register their interest in receiving a specific event type for a specific FI. When that event is received Event Management will send the event to the registered processors.

The original design of Event Management was a bit broader than this primary purpose, adding the responsibility of managing alert subscriptions and exposing alert processor definitions that are then used in the notification settings widget. These functions are still supported for backwards compatibility, however new development should use the newer Message Management processor template. As of version 3.10.0 Event Management no longer is responsible for maintaining alert subscriptions for event management processors. Alert subscriptions for Event Management processors are now maintained in the Alkami.MS.MessageSubscription.Host service. Event Management will proxy subscription management requests through to the MessageSubscription service to maintain backwards compatibility.

#### What types of events does Event Management support?

There are currently 3 types of events that Event Management supports, Broker Events, Custom Events and Cron Events

- Broker Events are any event that is broadcast via the Broker service, including events like a Login, Transfer Succeeded. These events are defined with a well defined set of parameters for each event.
- Custom Events are events that are triggered via a WCF call to the Event Management TriggerCustomEvent endpoint, and they can contain a custom event payload
- Cron Events are events scheduled using a Cron expression defined by the processor when it registers. Unlike the other types of events, only 1 processor will be triggered when the cron event fires.
#### What is the lifecycle of an event?

As of version 3.10.x the event lifecycle is as follows:

- Event Management receives an event
- Event Management looks for currently registered processors that have declared that they need to receive that type of event. There registrations are stored in the event.Configurations table
- If the configuration has the UseLegacySubscription flag set to true then the legacy event.Subscription table is used to find any user subscriptions for the matched processors. An event is sent to the Alkami.MS.EventManagement.Dispatcher service for each subscription, with the event containing the original event data plus metadata about the processor and the subscription dataFor matched processors that are mandatory, if there were no matching subscriptions then the event is still sent on to the Alkami.MS.EventManagement.Dispatcher
- If the configuration has the UseLegacySubscription flag set to false then the event.Configurations.WorkflowSteps column is used to determine the workflow that the event will be sent through.If WorkflowSteps is null then it is assumed that the processor is a legacy processor made using the Event Management processor template, so a default workflow will be used with 2 steps, first Alkami.MS.MessageSubscriptions.Host and then Alkami.MS.EventManagement.Dispatcher. Alkami.MS.MessageSubscriptions.Host is responsible for adding any subscription data to the event. If there are no matching subscriptions then the event will be discarded unless the processor has been declared as mandatory.If WorkflowSteps is not null then we will use those registered steps to define the steps the event will flow through in the workflow. ### Before you begin

Using the command line on your application server, execute the following command to install the Microservice for the first time, or after removal.

| choco install Alkami.MicroServices.EventManagement.Service.Host. -y |

To upgrade the microservice if it is already installed use this command instead:

| choco upgrade Alkami.MicroServices.EventManagement.Service.Host. -y |
