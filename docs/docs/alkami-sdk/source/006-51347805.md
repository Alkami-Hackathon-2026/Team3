## Intended Audience

This document has two intended audiences. The first will be Alkami staff, and will be prefaced "Alkami staff:" and which generally has no impact on the any non-Alkami staff who may be implementing any changes. The second audience is the technical staff of the SDK consuming client. This document is technical in nature and will generally only be applicable when used in conjunction with a working knowledge of the ORB technical system.

## Introduction

It is anticipated that the first walkthrough of this procedure will initially be done with the guidance of an Alkami SDK Support team member, but subsequent processes can be applied by a technical team member without the Alkami team being present.

The name of the new development environment is called a tenant. A single tenant is correlated with a given url and has a separate configuration. This is distinct within a given financial institution as the FI will have several related tenants (dev, qa, staging/UAT, production) in the various environments.

Certain environments will not be covered under this document without extensive modification, such as "testing core conversion". Additionally, managing multiple versions of a tenant are not covered under the scope of this document. If the implementing client wishes to pursue this on their own, they are welcome to submit targeted questions to Alkami SDK Support.

## Anticipated Prerequisites
### Database

This is a planning option only, and not a requirement. We advise centralization of your configured tenant database to keep things as simple as possible for your team.

The alternative option is to let each team member have a "duplicate" tenant environment locally with each SDK VM having the same configuration of a private database. This option would mean that the tenant database would need to be backed up before each SDK upgrade, and will be migrated individually during an SDK upgrade. Not a tremendous amount of additional work, but additional work.

To create the centralized SQL server instance would require a VM configured in the same "workgroup" (not domain) as the Alkami SDK VMs with the same local account names setup as on the SDK VM so that credential sharing would be possible for the database connectivity for the various Alkami service accounts (BankService, CoreService, etc, have their own connectivity to the databases).

Potentially just "repurposing" an existing SDK VM with IIS disabled as the "remote database server" is a valid and viable solution. There may be network name collisions in this case but the IT department should be able to resolve that.

If your team would like to pursue a more robust database option, such as domain joined, please arrange to have a phone call with the head of the SDK Support team to discuss potential options. The work for this is rather complex and not recommended for "simple SDK work".

### Core connectivity

We would ask that each SDK environment (either physical machine, or virtual machine) that is going to be so converted would have access to any core provider instance for testing. The minimum requirement is that the given SDK machine would be able to telnet to the expected target machine. This only applies to data required for the "test-core" (non-production instance) that will be used for member details, account syncing, transaction syncing, and similar related details.

### Core/third-party credentials

Our configuration script will provide all of the necessary working parts to make your SDK VM tenant environment match, however we do not provide credentials as part of this process. This would include credentials for any environment you want to connect to, including core or third party providers such as eStatements, check reorder, etc. Those services that you would connect to also may require additional whitelisting, so we are asking you to consider those in advance of the call and help ensure that any such service is appropriately whitelisted ahead of time, as well as credentials acquired/configured.

## Definition: Master Script

The Alkami Tenant Master Script is a holistic SQL script that contains all configuration of the ORB system that is not readily accessible through the Admin system (such as Content) and some things that are (Package Management).

While the script is lengthy, and potentially confusing, it is a series of repeating sections, where each section (provider, widget, banksetting, billpay, themes, etc) is self-contained into a temporary table. The final section of the script is a sequence of merges from the temporary tables into the final database configuration.

The output of the script is fairly complex and useful for the Alkami Delivery Group for examining changes to the system. The script is kept in sync with the staging environment for clients pre-delivery, and after delivery is fairly static (not necessarily key up-to-date). The script can be refreshed from the staging environment at relatively short notice, and should re-create the staging environment configuration by delta.

This script is initially supplied with a rollback transaction at the end of the code. This is intended to help review the configurations that will be changed.

The script should be tested once in rollback before applying any changes. After validating the changes that will be applied, and confirming that the changes look correct and expected, you can then apply the script with commit transaction enabled instead.

This script will produce output in the form of many tables. These tables are for review, and are not saved anywhere. Any desire to save these should probably involve saving to CSV or using Excel (or another spreadsheet program) and copy-pastes. One tab per output would allow for efficient followup with Alkami staff. Some of the copy-pastes of this output may be quite large, especially at a first run.

One of the output tabs will include a set of "REPLACEME" update statements. These are typically the secure values requested to be acquired before the configuration process. This segment will allow you to identify and provide the required values in a more compact manner.

Once this is applied, the developer should have a fairly consistent environment mirroring the client's staging tenant database, with URLs updated for the local environment appropriately.

## General Process Overview
- Alkami to prepare a one-release use conversion package
- Clone of the existing DeveloperDynamic database on one machine.
- Insert tenant and remove old users (Brady, etc)
- Apply Alkami provided master script to tenant.
- Apply registration settings
- Create site in IIS
- Apply configuration changes for database and hosts
- Restart IIS and services
- Test.

Each is now explained in more detail.

### Prepare a one-release use conversion package

Alkami staff: This task is only pertinent to Alkami staff.

- Determine the new environment URLs for use. You will use this in the "How to create a new tenant database" scripts as well.
- Check with TI to ensure if there are any caveats to the script preparation.
- Run the GenerateSDKTenant powershell tool with the appropriate tenant inputs.
- Check the core provider for additional configuration elements that may have been missed by Delivery-TI for confidential information. Ex: AUTHENTICATION_TOKEN
- Review entire script set as prepared to look for sensitive information such as passwords in any configurable setting field.
- As the script should now contain no sensitive information (passwords, secure credentials), attach the zip file output to the appropriate services ticket.
### Clone the existing DeveloperDynamic database

Alkami has provided a script in the template package uploaded to the ticket that can handle this task. See 1 - Backup-Restore.

If you are trying to recreate the database from scratch, a simple "delete database" through SSMS (close connections at the bottom too) would let you re-start this process.

If you are hoping to use a centralized server, run this on a local machine first, then do the backup and restore manually to move it to a new server. Alkami can assist with this effort.

### Insert tenant and cleanup some user values

Running script 2 - insert-tenant will do some cleanup on the users and insert the tenant into the tenant table. If you are using a centralized database store, you only need to do the insert at the top and change the target server on additional machines after the first.

### Apply Alkami provided master script to tenant

Apply the 3 - master script. See previous section (Definition: Master Script) for more details on the master script.

### Apply registration field sql if supplied by Alkami

Apply any registration field scripts provided by Alkami, then run script 4 - users and registration to ensure that the fields will allow for the simplest registration strategy. If your team needs a more complex internal configuration for testing registration, the Alkami team can assist with this as a future SDK Support Incident but for initial testing requires that the simplest changes be made.

### Create the site and bindings for testing

At this point run the powershell command 5 - iis site add to create the site with the specified bindings and add the necessary hosts entries.

### Apply any necessary additional configuration

Apply any environment specific changes such as additional test-core host entries or database updates for configuration. Failure to do so will almost certainly result in a failure. During your first setup, Alkami will assist in any debugging efforts. Typical requirements are a host entry and a change to the core provider.

### Restart IIS and Radium

Please run the powershell command iisreset and then in the services pane, restart the Alkami Radium Scheduler Service.

### Test

Test at the URL provided by Alkami and in the scripts. The site may take a minute or so to spin up.

The first task is user registration, but after that you should be able to log in as per normal. Note that an Entrust environment is not provided, and there is no email or SMS support "out of the box" for this test environment, so "Questions" is the preferred SDK environment login.

Any of the communication (SMTP, SMS) configuration that would be needed will likely require an additional SDK Support Incident to configure as various groups at Alkami would need to be involved, especially with regard to licenses and any associated fees.

As part of the sync process for login testing, please ensure the Radium service is running.

#### Sync overview

The Alkami login sync process consists of three principal components:

- Account sync - this process is synchronous and happens during the login workflow
- User sync - this process is asynchronous and happens as the user hits the dashboard. This process may be delayed as the user works through the site dependent on load.
- Transaction sync - this process is asynchronous and happens as the user hits the dashboard. This process may be delayed as the user works through the site dependent on load.

There may be other sync tasks involved for a given site configuration, and in the testing environment this may complete much faster than a full production workload. If the values have not synchronized in a timely fashion, ensure Radium is running, and try logging out and in again.
