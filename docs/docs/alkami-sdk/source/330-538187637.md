## Overview

Currently there are a myriad of problems with our current WebViews in the mobile application primarily around providing widget teams the customization options they need to make their pages look and feel like truly native experiences. Some of these issues are no native feeling transition animations, improperly showing the top and bottom bars, and scrims not overlaying certain elements. This solution utilizes query parameters of a url as well as a bi-directional JavaScript hook in order to achieve a more native look and feel of these WebViews.

See this presentation (https://docs.google.com/presentation/d/1JB8ujJ6h-YGfyAgziidBdZztjqUKj3rqATg51BdDmYk/edit#slide=id.p) for a more in-depth overview of the issues and how this approach attempts to solve them as well as this UX focused page (https://confluence.alkami.com/x/a-zaFw) about the problems and ideal solutions.

## Why Use Query Parameters?

Utilizing query parameters to trigger this is a non-conventional approach but in our case solves a unique problem where a web page may need to navigate to a new webpage but wants it to feel like a new experience in the application such as clicking a list item and navigating to a details page or having a specific page slide up over the current page.

Query parameters allow us to listen to all URL changes within the WebViews and intercept these to apply specific transitions and layouts where applicable.

## Sub-page isSubPage=true|false

The most important query parameter in all of this is isSubPage as setting this to true is what tells the mobile application to not render that route in the current webview, but instead create a new webview and apply the other layout/animation options to that new webview. This essentially is the hook that tells the mobile app that it needs to handle this route slightly differently than if I were just routing to a new page in the webview itself. This hook is what allows all the future params to be respected. In addition, setting this to true is also what tells the mobile app that you don't need the main bottom bar navigation on this route, which forces the user to back out of the flow instead of navigating to a different section of the app.

eg. isSubPage=true

and isSubPage=false

Notice how the bottom navigation tab is automatically shown when isSubPage=false this gives much more control when developing pages to making them feel like true native experiences.

## Top Bar showTopBar=true|false

The top bar visibility is controlled by the showTopBar query param. true will show the top bar on the page false will hide the top bar and have the webview take up the entire screen.

eg. showTopBar=true

And showTopBar=false

Since this ties into the existing routing logic, your existing top bar type and things such as the refresh-nav endpoint will still work out of the box with this approach

## Transition Animations transitionAnimation=slideInFromRight|slideInFromBottom|none

When navigating to a new subpage, the specified transitionAnimation will play. This allows the page to tie into predefined animations on the device so the animation that plays is 100% native, requires no custom CSS/JS code to mock a transition, and can be seamlessly updated in the future to apply the latest animations on the device if design paradigms ever change without needing to update the widget code.

## Javascript hooks
### showTopBarScrim

This is a Javascript event that the WebView invokes which tells the Flutter app to display a scrim over the top bar if a top bar exists.

See Webview JavaScript Actions#showtopbarscrim for more details.

### onTopBarScrimTapped

This is a Javascript event that is fired off from the Flutter app to the webview to tell the webview that a user tapped the scrim and the webview should dismiss its modal/bottom sheet content.

See Webview JavaScript Actions#ontopbarscrimtapped for more details

## Troubleshooting External URL Widget Display Issue

Problem

The client, ICCU, wanted to create a widget using a custom external URL in NAV builder. On mobile devices, the widget failed to display the bottom navigation bar, a key component of the user interface.

Root Cause

The issue was related to the configuration of the custom URL widget. When attempting to use an external URL and create a widget via the custom URL setting in NAV builder, the bottom navigation tab was not included when the widget was launched on mobile.

Resolution

To resolve this, we implemented a new widget using the GenericUrlLauncher. This tool is designed to properly launch external URLs within the Alkami platform. Then set up in NavBuilder using widget instead of custom URL.

The key settings we used were:

- Provider StandardSSO: GenericUrlLauncher
- Provider Name
- DisplayLocation
- Method: Get
- URI

By setting the display setting to "New Window," we prevented the external URL from being loaded within an iframe. This ensured the bottom navigation bar remained visible to the user, as the external site opened within Mobile. If the FI prefers iframe display setting can be set to Inline.
