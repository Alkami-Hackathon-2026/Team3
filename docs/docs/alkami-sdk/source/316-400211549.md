## Overview

Card Management facilitates the different actions a user can do on their cards. For example, it allows the user to register or activate a card, set limits, block/unblock a card, and set travel notifications. Card management SDK development allows a financial institution to develop their own card provider, customizing every action that Card Management supports on the back end provider service, while using the Alkami Card Management Widget as the user interface for their users.

### Creating a Custom Card Management Provider Microservice
#### Visual Studio Template

Alkami's Card Management Provider template will create a microservice to manage member cards.

```
choco upgrade Alkami.SDK.Templates
```

#### Setup
##### Provider Configuration

After a new Card Management Provider project is created, it needs to be configured in the database. There are two SQL scripts provided in the ProviderScripts folder to achieve this. The insert_provider_setting.sql script will install the provider as well as configure any included provider settings. The ExampleMappingConfiguration.sql script will configure the provider's capability mapping, which determines what actions are supported for each card type. Capabilities must be setup in the provider's capability mapping in order to be available to the end user.

To use these two scripts, modify any parameters as needed and then execute the transactions in the appropriate database.

Verify The Configuration

Using the same query to select our Card Management providers, verify your results look similar to this (your custom provider name will be different). At this point in the tutorial, there should be one entry for your custom provider in the Provider table and two entries in the Item table corresponding to the Localizable Resource and Connector ItemTypes. If any provider settings were configured in the script, these will be added to the ItemSetting table and will be associated to an Item on the ItemId field. There should be one record for every provider setting.

##### Running the Service:

Build the solution and Start the debugger in Visual Studio. A CLI window should appear and the service should connect with the running Subscription Service.

Ready To Test!

You're now ready to test! You should go through the previous section where we tested the Card Management provider and do the same routine for this new custom provider microservice we've created.

### Custom Provider Microservice Contract methods
### GetProviderCapabilitiesAsync:
- Accepts a GetProviderCapabilitiesRequest object.
- Returns a GetProviderCapabilitiesResponse object with a list of capabilities supported by the provider.

This method lists all capabilities supported by a provider.

This method is required by the Admin widget in order to display the list of supported capabilities on the Capability Mapping tab. From this tab, the user can select which capabilities are enabled for specific card types for each provider that an FI uses. The list of supported capabilities then gets filtered by the orchestration service (Prism) using the mapping table settings (as shown below) to determine which capabilities to enable on the UI.

Provider capabilities correspond to actions that can be performed with the InitiateCardAction method.

### GetCardsAsync:
- Accepts a GetCardsRequest. The properties that are marked mandatory should be populated for the provider service to function as expected. Refer to the tables below for details on this request object.
- Returns a GetCardsResponse object which contains a list of Cards for the user.
- A filter CardBinsToInclude is recommended to be added in the provider to filter the cards by BIN.

This method retrieves cards and card properties from a provider, and then maps the results to an Alkami Card record.

### CVV and PIN update:

When CVV or PIN is transported from UI to provider or vice versa, the data is sent in the Card.CVV field. Contracts will be modified in the future to have PIN use a different card field rather than using CVV field. But for now, PIN uses Card.CVV field. The data has to be encrypted before sending using the key found in cert "Alkami Mutual Client" and decrypted using the same key on the other side. Here are the two use cases laid out with specific steps:

#### Fetch CVV:
- User will request CVV.
- The request will go to the applicable provider.
- The provider will fetch the CVV and encrypt it using the key found in "Alkami Mutual Client" cert.
- The provider will store the data in the Card.CVV field and respond back with the card object.
- UI will extract the data from Card.CVV and decrypt the information for the user.
#### Update PIN:
- User will update the PIN on the UI.
- UI controller will encrypt the PIN and store it in the Card.CVV field.
- The request will go to the applicable provider.
- The provider will retrieve the PIN from the CVV field and decrypt it using the key found in "Alkami Mutual Client" cert.
- The provider will update the new PIN.
