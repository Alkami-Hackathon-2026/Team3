## Setting Up Scenarios

Scenarios are at the heart of the philosophy of end-to-end testing. They allow us to emulate user behaviors, and ensure that our application is always built to perform in each scenario.

Every Scenario is made up of a few different pieces:

- Scenario Specs
- Test Modules
- Mock Services (Data)

To start, we'll need to come up with a few scenarios for our user to go through. Scenarios, just like in Unit Testing, can be anything in the realm of Expected Scenarios (also called "happy path") or Error Scenarios (also called "sad path"). Happy Path testing is usually the easiest to conceive, but it is imperative that we reserve a scenario for reasonable error scenarios that we can ensure our application breaks when it needs to break.

For our Example Scenario, we'll leverage the StandardSSO widget's AccountInput Scenario.

For this, we'll need to:

- Render our widget using MirageJS
- Prepare our Scenarios and Test Cases
- Write our Test Cases
- Mock API requests and responses

We'll use the post method to define our route, and we can return a Response instance to give our mock response.

- new Response( status, headers, data )

### Defining our Scenarios

Now that we have a way to render our widget, we can define each Scenario within the "tests/e2e/specs" directory of our project. A scenario is made of two parts:

- Setup — Tells Cypress what URL to go to, viewport size, and anything else we want to do before any tests are run
- Module — Contains the test cases that will be run in our scenario

We split each of these into two separate files so that we can separate concerns for readability and maintainability purposes.

Let's look at the files we're going to leverage for implementing this structure:

- tests/e2e/specs/accountInputScenario.js — Scenario Setup
- tests/e2e/modules/accountInputTests.js — Module containing our Test Cases
test/e2e/specs/accountInputScenario.js

```
// https://docs.cypress.io/api/introduction/api.html
import accountInputScenario from '../modules/accountInputTests';

describe('account inline selection scenario', () => {
describe('desktop', () => {
beforeEach(() => {
cy.visit('/accountInputInlineScenario');
cy.viewport(1000, 1000);
});

accountInputScenario();
});

describe('mobile', () => {
beforeEach(() => {
cy.visit('/mobile/accountInputInlineScenario');
cy.viewport(375, 812);
});

accountInputScenario();
});
});
```

tests/e2e/modules/accountInputTests.js

```
// This is our accountInputScenario() function as imported in specs/accountInputScenario.js
export default () => {
it('prompts the user to choose an account', () => {
// Open Iris Dropdown
cy.get('#iris_dropdown_account')
.click();

// Click on first option
cy.get('.iris-dropdown__display-list')
.first('.iris-option')
.click();

// Click on the launch button
cy.get('.header__actions .iris-button')
.click();

cy.get('#_iframe')
.should('exist');
});

it('allows a user to go back and choose a different account', () => {
// Open Iris Dropdown
cy.get('#iris_dropdown_account')
.click();

// Click on first option
cy.get('.iris-dropdown__display-list')
.first('.iris-option')
.click();

// Click on the launch button
cy.get('.header__actions .iris-button')
.click();

// Click the back button
cy.get('.render__navigation .iris-button')
.click();

// Make sure the dropdown has been cleared out from previously selected account
cy.get('#iris_dropdown_account .iris-dropdown__placeholder')
.should('contain', 'Select an account');
});
};

```

More information on Syntax and Structure can be found here on the Cypress documentation website (https://miragejs.com/docs/testing/application-tests/). However, you'll notice that the syntax and API is incredibly familiar and mirrors much of the testing syntax that we're already used to with jQuery (or document.querySelectorAll) in addition to .should() style testing.
