## Overview

The SDK contains a functioning Online Banking (OLB) system. Of course this means that it includes the databases which are needed for such a system. This page contains a simple rundown of the tables that are typically of interest to SDK developers. As an SDK developer, you will never read or write directly from the database tables from within your SDK projects. However, a basic understanding of these tables will help you to understand how the system works, and will show you where you can update values in the SDK databases to facilitate testing your SDK projects.

## The Databases

Within a working Alkami SDK system you will find two databases that are required for the system to work (sometimes you will find additional databases as explained below). You can use the Microsoft SQL Server Management Studio (SSMS) to explore the databases.

| Name | Description | aka | Notes |
| AlkamiMaster | There is one "Master" database in the system. This database contains tables for system-wide functions like task scheduling. You will not need to worry about those functions. However, there is one table that you need to understand and it is the core.Tenant table (see below) | Master | |
| DeveloperDynamic | This is the database that contains all configuration settings, and data for a specific financial institution (FI). The FI "DeveloperDynamic" is a fictitious name used for the example FI within the SDK. Within a default installation fo the SDK, this database contains some dummy users, and dummy accounts and balances for the users. | Tenant | |
| Other database(s), typically named:AlkamiYourFiName_Dev | (optional) This is the database that contains configuration settings, and data for a a test/dev instance of your FI and generally includes configuration settings to connect the SDK to your a test instance of your core processing system in order to view accounts and balances, etc. that are pulled from an actual core. | Stage-Match orStage-Match Tenant | If you have one or more of these databases, they will have been created by making a copy of the DeveloperDynamic database and then applying many of the same configuration settings that your FI has in the Alkami stage environment. |

## Master Tables

As mentioned above, there is only one table which you need to understand.

| Name | Description | Notes |
| core.Tenant | This table is used to map incoming requests to the proper tenant database. For example, the default row in this table contains 'developer.dev.alkamitech.com' in the BankUrlSignatures column, 'localhost' in the DataSource column, and 'DeveloperDynamic' in the Catalog column. Thus a request coming into the website for the site developer.dev.alkamitech.com will be processed using the DeveloperDynamic database in the SQL server on this same machine. If you have a stage-match tenant database, there will also be a row in this table mapping a different url to the stage-match tenant database. As you can imagine, the Alkami production systems contain a large number of rows in this table-- one for each financial institution in our system. | There is also a ConnectionString column in this table that needs to be configured with the proper source and database for the OLB system to come up properly. |
