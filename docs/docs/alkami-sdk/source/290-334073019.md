| Staging |
| Monday-Thursday | 7:00pm CT |
| Production |
| Sunday, Tuesday and Thursday | 10:30pm CT |
#### Getting Ready for Prod Deployment

For a submission to be picked up by the Release Management teams automation, approvals must be given and the ticket must be transitioned by the SDK team from Awaiting Configuration to Waiting for Prod Deployment. SDK Submission tickets are not monitored so the SDK team relies on being tagged in a comment on the ticket as a notification that there has been movement so that we can act on it. When transitioning tickets, by clicking Stage Validation Passed, you must leave a comment that the submission has passed testing and make sure to tag sdksupport in that comment. You must also address the configuration questions in the comments on the ticket after you have made that transition. Without a comment confirming if configuration is required, the SDK team won't transition the ticket and the submission will not move forward. Tag sdksupport in that comment as well.

#### Cutoff Time

The cutoff times for the deployment windows are listed below.

| Staging | |
| 4:00pm CT | Submissions have passed the validation process and SDK team code reviews by 4pm the same day and are queued by Submitter via One-Click Deploy functionality |
- If a submission doesn't make it into the 7:00pm CT slot due to it missing the deadline it will go in the following 7:00pm CT slot if available.

| Production | |
| 10:30pm CT | Submissions have to be transitioned as noted previously by 2 pm the day of deployment. If this deadline is missed it will deploy in the next available slot. |

The submission deployments can be affected and shift based on a couple of factors regarding production deployments where they do not go into the next available window. The first would be code freeze dates that we put into place and nothing will be deployed during that time without an escalation. The collateral damage of a code freeze can be the number of approved and queued deployments can cause an overload that will have to be spread out over two or more deployment windows. This can also happen outside of code freeze but it is rare. There are also times when a pod will have a deployment scheduled for a specific window, which will cause other deployments for that pod to shift. As an example let's say today is Monday and Pod 1 has a deployment scheduled for Thursday. You have all of the approvals in place for your submission and are expecting your deployment to happen on Tuesday but since you are also in Pod 1 your deployment gets scheduled for Thursday. This helps with bandwidth for the Release team and ensures the uptime for everyone on that pod by consolidating the deployments.
