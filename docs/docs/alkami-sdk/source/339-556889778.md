## Overview

The Standard SSO provides a generic means, through configuration, to interact with a wide variety of SSOs. The following documentation will provide insight into constructing the JSON configuration for the service. For SAML implementations, StandardSSO supports SAML 2.0

### Expression Capable Locations

The following locations allow for expressions:

- HttpRequest → Uri - Allows for Relative or Absolute URIs. This means that validation will be limited to the URI not being null or whitespace.
- HttpRequest → Body
- HttpRequest → FormFields → Values
- HttpRequest → Headers → Values
- HttpRequest → QueryParameters → Values
- Methods → Values
- Services → Http → Uri
- Services → Http → Body
- Services → Http → FormFields → Values
- Services → Http → Headers → Values
- Services → Http → QueryParameters → Values
- Services → Http → Thumbprint
- Services → Saml → Request → Subject
- Services → Saml → Request → Attributes → Values
- Services → Jwt → Request → Payload → Values
- Services → Jwt → Request → Headers→ Values
### Authentication

Authentication if required is usually provided through Headers in the HTTP request and can also be accomplished through a certificate specified by the thumbprint. For more information on HTTP Authentication (https://developer.mozilla.org/en-US/docs/Web/HTTP/Authentication) and HTTP Authorization (https://developer.mozilla.org/en-US/docs/Web/HTTP/Headers/Authorization).

### Validation Library

Validation Library

As part of the Standard SSO Microservice, the validation logic was separated out into an independent .NET Standard 2.0 library (Alkami.MicroServices.StandardSSO.Engine (https://packagerepo.orb.alkamitech.com/feeds/nuget.dev/Alkami.MicroServices.StandardSSO.Engine)). The library was created to support validation outside the context of the microservice.

It can be leveraged to perform the same validation as the service, but must be kept in sync with the library used within the microservice.

### ClientHttpRequest
#### AutoLaunch

The autoLaunch setting is a boolean value that will default to true if the setting is not specified in the configuration. The following behavior for the autoLaunch setting will be:

- When autoLaunch = true, Standard SSO will automatically open the SSO
- When autoLaunch = false, Standard SSO will disable the SSO from automatically opening so that users are able to see the description of the SSO and launch when they choose to.

AutoLaunch Example

```
{
"BankIdentifier": "0cacb7d7-631e-4b81-a80a-fd94e569bd35",
"ProviderName": "GenericUrlLaunchV2",
"Description": "GenericUrlLaunchV2",
"HttpRequest": {
"AutoLaunch": "false",
"DisplayLocation": "NewWindow",
"Uri": "https://www.visa.com/atmlocator/#(page:home)",
"Method": "Get",
"ContentType": "application/json"
}
}
```

### AccountConfiguration
#### CoreNames

Limits the accounts to those that have account types that match the CoreNames specified in this array.

#### AllowedRelationshipTypes
- Unknown → 0
- PrimaryOwner → 1
- JointOwner → 2
- Linked → 3
- Aggregated → 4
- BusinessAccount → 5

This setting is used in two scenarios to limit the scope of available accounts to be used by the widget.

- When displaying accounts to be selected in the account dropdown, will display the accounts that satisfy this condition.
- When processing a request for a specific account, it will only do so if the selected account satisfies this condition.This check needs to happen because the user might be redirected from another Widget (i.e. MyAccountsV2 or CardManagement) and we need to make sure the pre-selectected account satisfies the condition.
#### Permissions

Limits the accounts to those that the user has permissions for that match the specified in this array.

#### BIN Filter

A List of BIN's that will be INCLUDED in the account and card request. Filters the cards by the card number and the accounts by the credit card number.

#### Extended Properties Filter

A List of extended properties that will be included in the account request. Filters the accounts by matching Account's extended properties with these given list.

#### IncludeAccountTypes and ExcludeAccountTypes

IncludeAccountTypes and ExcludeAccountTypes under AccountConfiguration provides a method of filtering accounts based on account types. The following Account Type enumerations are available for configuration:

- AssetAccount
- AutoLoanAccount
- BalanceOnlyAccount
- BusinessAccount
- CertificateAccount
- ClosedEndedLoanAccount
- CoreOnlyScheduledTransfer
- CreditAccount
- CreditCardAccount
- DemandDepositAccount
- ExternalAccount
- MoneyMarketAccount
- MortgageLoanAccount
- OpenEndedLoanAccount
- PayoffCalculatorDisplayed
- SavingsAccount
- InvestmentAccount
- IRAAccount
- HSAAccount

Please see example configuration here under AccountConfiguration AccountType Example.

In order for the configuration validation to pass:

- AccountType must be from the above list
- AccountType cannot be in both IncludeAccountTypes and ExcludeAccountTypes

Consider this edge case: account is both a BusinessAccount and SavingsAccount. If BusinessAccount is added to "IncludeAccountTypes" and SavingsAccount is added "ExcludeAccountTypes", the account will be excluded.

### BusinessUserConfiguration
#### RestrictSubUserAccess

A bool used to determine if Business Sub Users should have restricted access. If this is true and a Business Sub User attempts to access the SSO, an "Insufficient Permissions" error will be generated.

#### RolePermissions

Permissions that will be checked for a user to have, otherwise the user will see SubUserRestrictedAccess.

#### IgnoreSubUserViewSummaryPermission

This will only be applicable to business sub users. When accounts are fetched ViewSummary permission is always checked for a user. This configuration will allow to skip ViewSummary permission check on accounts for business sub users only when set to true. Default value is false.

### UserConfiguration
#### RequiredExtendedProperties

A list of extended property that will determine if User can access the SSO. If User's extended properties do not contain any of the given extended property, an "Insufficient Permissions" error will be generated.

### FdicConfiguration
#### IsSpeedbumpRequired

If set to true and FI has any FDIC signage enabled, will show a speedbump warning that the user is going to a non-FDIC insured product prior to initiating sso.

When speedbump is shown, the autolaunch setting will be ignored.

Here is an example of a config that has FDIC required. You also will need FDIC configured at the FI level for this to work properly. As well as RemoteTheme enabled.

FDIC Example

```
{
"BankIdentifier": "D4CB91AA-3C75-47EE-980D-2E3783A2DFBE",
"ProviderName": "FDICTest",
"Description": "FDICTest",
"HttpRequest":
{
"DisplayLocation": "NewWindow",
"Uri": "https://www.google.com",
"Method": "GET"
},
"FdicConfiguration":
{
"IsSpeedBumpRequired": true
}
}
```

This is an example of what you will see in StandardSSO if the Speedbump is enabled properly. This shows up when you first attempt to launch into the client site. Either when you first land on the page and not options are present, or after you have selected an option and clicked launch. You must accept this in order to launch the SSO.

If you are having issues with FDIC configuration try looking here: FDIC Compliance Troubleshooting Runbook#OverviewOverview (/pages/viewpage.action?pageId=437944496)

### Customizing Display and Navigation Behavior via Query Parameters

Videos: https://drive.google.com/file/d/1t-8vWbblrBKl3Asw20yUBefr7iLUYAEV/view (https://drive.google.com/file/d/1t-8vWbblrBKl3Asw20yUBefr7iLUYAEV/view)

When linking to a Standard SSO from another widget, the display and navigation behavior can be customized via query parameters in the url. Some examples to consider would be:

- How should we open a Loan Payment SSO (with a Standard SSO implementation) from the Accounts Widget via the Pay Now button?
- If my SSO opens a PDF file as a landing page, for example to have the user agree to a disclosure, how can I configure the Standard SSO widget to allow the end user to close the PDF file and still keep their session open in the platform. In some scenarios, when the the landing page is a PDF file, closing the PDF file actually closes the online banking window as well.
- If I initiate the SSO from a widget like Accounts or Quick Apply, how do I configure my Standard SSO widget to go back to the Accounts or Quick Apply after opening the 3rd party's SSO window when they hit the back button instead of going back to the Standard SSO widget?
#### Customizing Display Method

To change the display method from the option specified in the standard sso config, add the query parameter displayMethod to the link's url.

```
/StandardSSOUrl?displayMethod=SameWindow --Opens the sso in the same tab/window (_self)
```

```
/StandardSSOUrl?displayMethod=NewWindow --Opens the sso in a new tab/window (_blank)/StandardSSOUrl?displayMethod=Inline --Opens the sso in an iframe
```

Implementation Recommendations:

When "?displayMethod=SameWindow" is used, only a loading spinner will be displayed in the standard sso widget. This is usually a better user experience instead of displayMethod=NewWindow since the standard sso widget will be fully visible to the end user before opening the 3rd party site.

Here's a screenshot of the flow when "?displayMethod=SameWindow" for Desktop

Here's a video for the same "?displayMethod=SameWindow" for iPad using a Generic URL widget that redirects the user to an external site from the Accounts Widget.

#### Customizing Navigation

When opening a standard sso from a link, the expected behavior when the user closes the tab or clicks the back button is that they are returned to the widget which opened the sso, not the standard sso widget. As an example, if the end user opens a Mortgage Transaction SSO from the Accounts widget via the "View Transactions" button, we would want the user to go back to the Accounts widget when they exit the 3rd party's site.

To accomplish this, add the query parameter backUrl to the link's url.

/StandardSSOUrl?backUrl=WidgetToGoBackTo --When user clicks back from the SSO, they should be back on the original widget

##### Native Apps

Through the use of the Flutter App and the dispatched events surrounding the webview (webviewActive and webviewInactive) we're able to properly identify when a user is returning back from an SSO and send them to the calling Widget via the backUrl query string being used. Unfortunately backUrl doesn't work as expected on iOS and Android app and some documentation can be found on DEV-118319 (https://jira.alkami.com/browse/DEV-118319) - Getting issue details... STATUS .

On chromium based browsers (Chrome, Edge), pages that quickly get redirected are not added to the browser history. The backUrl query parameter will still need to be used to support other browsers.

The iOS native app supports a query parameter to open links in a browser, instead of an in app WebView. This should be handled in the standard sso config by adding the query parameter "target": "browser".

#### Forcing IFrame use on Native

The forceiframe query param can be used to not override "inline" display method on native. This only applies when the display method is inline and the user is on native. Please reach out to carbon team if considering using.

```
/StandardSSOUrl?forceIFrame=true
```

#### Different SSO display settings for mobile and desktop

There may be times where we want different devices to display differently. An example of this that we have run in to is when an SSO loads slowly enough to trigger the safari popup blocker. In this case we could want desktop to target _blank (new window) and mobile to target _self (same window) to avoid the SSO being stopped by the popup blocker. At the moment the most reasonable solution we have found to this sort of issue is to create a second provider and widget for mobile, or use the navigation builder to append the displayMethod query parameter to override what is set up in the config. Here are the steps if you wish to do this

- Modify the below DST template, you want to create a copy of the SSO provider config and SSO widget for the device you are targeting, reference Widget display settings documentation to determine how to map providers to specific devices. - Navigate to the admin portal for the FI and environment you are making this change to, navigate to Setup => Navigation Builder
- If a navigation does not already exist then create a new navigation and give it an appropriate name
- Identify the widgets you are working with, move them to an appropriate bucket if needed
- Once the widgets are in the appropriate bucket, remember to update the query parameter under "Widget Subroute" in order to override the display setting
### Common Issues / FAQ
#### RSA Key Encryption Algorithm

The default algorithm for StandardSSO and GenericSSO providers RSA 1.5 (http://www.w3.org/2001/04/xmlenc#rsa-1_5 (http://www.w3.org/2001/04/xmlenc#rsa-1_5)), is now officially deprecated by the W3C and disallowed by NIST (SP 800-131A). While our IdP-initiated flow is not a primary attack surface for padding oracle exploits (like the Marvin or ROBOT attacks and other relevant CVEs), modern runtimes, e.g. Node.js 22+ have begun removing support for this primitive, leading to potential decryption failures at the Service Provider.

New Implementations

All new SSO integrations must use RSA-OAEP (http://www.w3.org/2001/04/xmlenc#rsa-oaep-mgf1p (http://www.w3.org/2001/04/xmlenc#rsa-oaep-mgf1p)) to ensure "secure-by-default" configuration and maximum compatibility with modern client environments.

Existing Implementations

Legacy providers remain functional and are not known to be at any risk but can be updated upon client request to meet modern hardening requirements.

Configuration Update

This applies to GenericSSO / Consolidated providers as well as both ultimately pull from the Saml20Utility where the deprecated default lives. To update a provider, modify the KeyEncryptionAlgorithm field in the configuration:

StandardSSO Example

```
"EncryptionParameters": {
"KeyEncryptionAlgorithm": "http://www.w3.org/2001/04/xmlenc#rsa-oaep-mgf1p",
...
}
```

Or pass the value in during EncryptionParameters construction in Consolidated:

GenericSSO Example

```
Saml20Utility.EncryptionParameters encryptionParameters = new Saml20Utility.EncryptionParameters
{
KeyEncryptionAlgorithm = "http://www.w3.org/2001/04/xmlenc#rsa-oaep-mgf1p",
....
};
```
