Before we can test, we're going to need a local development environment that we can use for testing our widget outside of ORB. This same environment will be leveraged for mocking out data that we can play with in our simulations. Thanks to MirageJS, this is very straightforward, and most of the work is already done inside of albus-module-cypress.

First, add the miragejs node module to your project:

```
npm install --save-dev miragejs
```

Now that we've got miragejs, let's review the structure of our local dev server folder:

Local Dev Server Structure

```
└── server # Miragejs mock server for albus-module-cypress e2e testing
├── index.ts # Contains createMockServer, which specifies mock server routes
├── mocks # Scaffolding and service response mock data
│ ├── entities # Mock data entities for API responses
│ │ ├── accounts.ts # Name this appropriately based on the entities it will contain
│ │ └── ...
│ ├── accountScenario.ts # Filename is identical to its associated E2E scenario. See "tests/e2e/specs".
│ ├── errorScenario.ts
│ ├── index.ts # Should export its siblings for easy importing
│ └── ...
└── ...
```

### createMockServer

Our Mock Server serves two purposes: to Render our widget, and Mock API requests and responses. Both of these are incredibly straightforward.

We'll start by defining our mock server in "server/index.ts"

In the example below, we're defining a route for our widget.

server/index.ts


Important

Mirage can be very pedantic with how it identifies the request URL to match to one of your defined routes. Make sure your namespace + route combination matches the URL you're requesting exactly – including the leading slash. If you fail to do so, you'll likely see errors in the console similar to:

Mirage: Error: Your app tried to GET 'StandardSSO/GetData', but there was no route defined to handle this request.
