Albus is built on the foundation of being opinionated yet incredibly flexible. With that in mind there are sane defaults that come set in both global and preset specific scopes and every value is available to override at a project level. This allows Albus to express opinions and make it easy to get started, while allowing for customization and unique needs that doesn't fall into the normal setup.

The pattern for configuring a project, is to create a file called albus.config.js at the root of your project folder. Whenever an Albus command is called against that project, that file will be read in, merged with the global and preset defaults, and then executed.

Presets and Plugins contain highly customizable configuration. Check the Presets (/spaces/SDKC/pages/303531412/Presets) section out to understand the available configuration options.

Let's take a look at a full config file to see what's available:

Annotated Albus configuration

```
module.exports = {
global: { // Options that are shared across presets
base: '.', // Base path for writing build files (defaults to cwd)
configPath: 'albus.config.js', // Path to Albus configuration (exclusively used by the cli)
debug: false, // Runs tasks in series and enables Debug flag in logs
deployFiles: [], // Glob of static files to deploy
deployIgnore: [], // Glob of static files to ignore during a deploy
deployPath: '/orb/<clientFolderName>/<areaFolderName>/<orbWidgetName>', // Path to dist folder
projectPath: './<projectNamespace>', // Path to project folder
rebuild: false, // Force rebuild of all assets when transmute is called
redeploy: false, // Force redeploy of all assets when deploy is called
verbosity: 'normal' // Logging level: 'verbose', 'normal', 'silent'
},
tokens: { // Tokens are values that can be interpolated in other configuration values
orbWidgetName: "TransferV2", // Widget Name to be used for deployment
clientFolderName: "WebClient", // Folder where Web Client is located ('WebClient' or 'WebClientAdmin')
areaFolderName: "Areas" // Folder where your project type gets deployed ('Areas' or 'Modules' are most common)
... // Additional custom tokens can be added for plugin configuration
},
presets: [], // Specify presets via string or require statement (empty array will search for albus-preset packages to include)
presetConfiguration: { // All preset specific configuration goes here
'presetName': { // Individual name of preset to be configured
plugins: [], // Specify plugins to enable that are available in this preset
pluginConfiguration: { // All plugins in a preset get a section of configuration based on their name
'pluginName': { // Individual name of plugin to be configured
pluginProp1: 'pluginProp1Value' // Plugin properties to override (defined by each plugin)
}
...
}
}
...
}
}
```

#### Writing your own Albus config file

As mentioned above, Albus allows creating a configuration file per project to customize what functionality is available from the presets installed. Since Albus comes with sane defaults, the config below is (sometimes) all that is needed for commands to be executed successfully against a project.

albus.config.js

```
module.exports = {
tokens: {
orbWidgetName: 'WidgetName'
}
}
```

This pattern of having a config file saved in the project, alleviates the hassle of specifying the tokens on the command line. With that said, if you would like to specify options via the command line, those will take priority over what is configured in your albus.config.js file, just as your configuration overrides the defaults.

In terms of merging values, the strategy is straightforward. An object will be merged with another object (just like Object.assign) and simple values or arrays will be overridden.

The merge strategy in detail is as follows:

- global and tokens use a simple merge. Any properties specified get added or replace the default (just like Object.assign).
- presets overrides the default if specified
- presetConfiguration uses a deep merge method through the following actions
- plugins overrides the default if specified

Each named pluginConfiguration item will be shallow merged with your configuration. This should act how one would expect except for maybe the case if the plugin has a deep Object configuration. In this case the plugin should dictate the merging strategy it needs.

If you need to see how the configuration is getting hydrated you can use albus scry to see a fully hydrated configuration file.
