### Install the microservice

```
choco install Alkami.MS.GenericProxy.Service.Host --source https://feeds.alkamitech.com/nuget/choco.dev/ -y
```

Note

Add www.google.com (https://www.google.com/) to the default whitelist for the provider. If you have trouble reaching it or get an error, use the admin site and edit the provider settings to add it and any other host and domains you must reach.

Networking must be provided any URL that you need to communicate with in production so that it can be whitelisted.

The following are the steps to add the URLs to the provider settings:

- Go to the admin site, admin-developer.dev.alkamitech.com.
- Go to Setup > Integration Settings to go to the provider settings.
- Click Providers and from Provider Types, select GenericProxy.
- Next to the Alkami.MS.GenericProxy, click Edit.
- For this example, you can add the following URLs highlighted in the screenshot.
- Click Save Changes and you can close the admin site.
- After updating the provider settings, type iisreset to bounce IIS from the command line.

### Add the GenericProxy Microservice to your Widget

Add the latest versions of the following NuGet packages to your Widget:

- Alkami.MS.GenericProxy.Client
- Alkami.MS.GenericProxy.Data

If you install the Alkami.MS.GenericProxy.Client package first it will install the Alkami.MS.GenericProxy.Data package as it is a dependency of the client.

Add this line to the .nuspec file for your Widget to ensure that the microservice assemblies are included when you build your widget.

<file src="bin\Alkami.MS.GenericProxy.*" target="lib" exclude="**\*.config"/>

Update the NuGet packages in your project to make sure they are up-date-date (except for any packages that might not be permitted)

Before you go any further, build the widget to confirm that everything compiles correctly.

### Building Widgets with Generic Proxy

This explains how to securely build widgets that interact with external APIs using Alkami's generic proxy service. Widgets can take different forms such as standalone API-driven widgets or embedded iFrame widgets, but all follow the same proxy-based integration model.

#### Overview

The generic proxy microservice provides a secure way for widgets to call external APIs without exposing sensitive credentials in frontend code. By routing requests through the proxy, developers can:

- Protect API keys and secrets
- Support tokenized authentication flows
- Enable seamless user experiences (i.e., SSO) without additional login prompts
- Maintain compliance with logging and traceability standards
#### Widget Patterns

Widgets typically follow one of two integration patterns with generic proxy:

- ##### Standalone API-Driven Widget
- Widget backend APIs securely through generic proxy
- API Responses are used directly to render UI inside the widgetExample: A component showing account data or 3rd party insights
##### 2. Embedded iFrame Widget
- Widget requests a tokenized URL from the backend via generic proxy
- The URL is embedded in an <iframe> to load an external application

#### Implementation Steps
##### STEP 1: Create the Widget
- Include server-side logic for API calls
- Route all API requests through generic proxy (never directly from the browser)
##### STEP 2: Configure API Requests
- Add authentication headers (API key/secret)
- Pass a member ID or equivalent user identifier in the request body
- Store keys/secrets in widget settings, not in provider configuration
##### STEP 3: Backend API Responsibilities

Your backend should:

- Accept the user identifier from the proxy call
- Generate the appropriate response:For standalone widgets: return data payloads.For iFrame widgets: generate and return a one-time tokenized URL
##### STEP 4: Frontend Integration
- Standalone widget: Render API response data directly in the UI.
- iFrame widget: Set the returned tokenized URL as the <iframe src="...">.
- (Optional) Implement keep-alive logic to maintain session continuity

#### Security Best Practices
- Use HTTPS for all communications
- Favor POST requests to avoid leaking parameters in URLs
- Use one-time-use tokens that exchange for JWTs
- Log actions at trace level (without PII) for troubleshooting

#### Benefits

By using generic proxy, widgets gain:

- Security: Credentials and sensitive headers never touch client code
- Flexibility: Works across both lightweight standalone widgets and embedded apps
- Seamless SSO: Enables smooth user experiences without login prompts
- Auditability: Built-in logging and observability for compliance

In short, generic proxy abstract API communication so widgets can securely fetch data or launch external apps, whether inline or via an iFrame, while ensuring user sessions remain seamless and secure
