Prerequisites

Alkami Accounts Product Guide (https://midas.alkami.com/downloads/accounts-product-guide/)

The Accounts widget is the member interface used to view Transaction Details. The Transaction Detail will contain the front and back images of a check. A developer must be familiar with this behavior before customizing it.

Samples and Tutorials (https://confluence.alkami.com/sdk/samples-and-tutorials-62701693.html)

You must complete the My First Widget (https://confluence.alkami.com/sdk/my-first-client-widget-78655984.html), My First Admin Widget (https://confluence.alkami.com/sdk/my-first-admin-widget-71995307.html), and My First Provider Microservice (https://confluence.alkami.com/sdk/my-first-provider-service-67617391.html) tutorials. This guide expects the developer to be comfortable creating and working with client widgets, admin widgets, and microservices.

A check image is the digital picture of the front side and back side of a paper check. An image is captured when a check is deposited and can be viewed as part of the details related to the transaction. These images are hosted outside Alkami's systems and must be linked to or downloaded and then rendered in the browser for the member to view. You can use Alkami's SDK to create a custom check imaging microservice to manage the retrieval of those images from an external data source.

## Set Up Check Imaging in the SDK

In addition to the base SDK install, developers must complete this guide to enable viewing of check images. The initial setup will build the infrastructure necessary so that a custom check imaging microservice can plug directly into the existing environment. We will address each numbered element in this diagram, installing and configuring one piece at a time. Along the way we'll touch on the importance of each piece and the types of issues the SDK developer must be aware of when building out a new microservice provider.

### Client Widget - MyAccountsV2 Accounts

The Accounts widget is part of the base SDK installation and must already be available.

#### Enable the Check Image Fields

To view check images, you must enable this feature.

Execute this script against DeveloperDynamic or your custom named database.

```
IF NOT EXISTS (SELECT ID FROM CORE.TransactionDetailGeneralField WHERE Field = 'CheckImage')
BEGIN
insert into core.TransactionDetailGeneralField (field, ordering, CreateDate) values('CheckImage', 5, GETUTCDATE())
END
select * from core.TransactionDetailGeneralField where Field = 'CheckImage'
```

Conditional Check Imaging

Adding the CheckImage field to the CORE.TransactionDetailGeneralField enables check images for all account types. This is practical for development, but it might not be configured this way in the higher environments. You can restrict check images to specific account types as well as account type classes.

#### AccountTypeTransactionDetailField

If you want to configure Check Images for specific account types, insert CheckImage in the Field column in [core].[AccountTypeTransactionDetailField] with the appropriate AccountTypeIds specified. This is a one-to-one relationship. Each account type needs it's own CheckImage entry.

#### AccountTypeClassTransactionDetailField

You can also configure Check Images on the Account Type Class level by inserting in the [core].[AccountTypeClassTransactionDetailField] table, making CheckImage the Field column value, and specifying the appropriate account type class id.

#### Update Transaction Detail Tab View

The views in the Accounts widget are dynamic and are configured by JSON objects stored in the database.

Execute this script to add the Check Images section and redefine the Summary section.

```

@WidgetId INT,
@WidgetSettingName VARCHAR (100) = 'transaction_information_sections',
@WidgetSettingValue VARCHAR (MAX) = '[]',

SET @WidgetId = ( SELECT ID FROM CORE.WIDGET WHERE NAME = @WidgetName)
SET @Found= (SELECT COUNT(*) FROM CORE.WidgetSetting WHERE WidgetID = @WidgetId AND Name = @WidgetSettingName)

-- INSERT JSON CONTENT TO WIDGET SETTING
SET @WidgetSettingValue =
'
[
{
Name: "Summary", /* The name of the tab. Do not change: The code will use this name to reference a tab*/
Title: "Summary", /*The title is the label or display value for the tab*/
AccountTypeClassFilter: "*", /* The asterisks (*) indicates the tab applies to all account types */
Sections : /* Sections containing columns within a tab */
[
{
Title: "",
ColumnsPerLine: "2",
Columns:
[
{
Title: "Description",
ExtendedPropertyName: "SpecificDescription",
ExtendedPropertySource: "Transaction",
FormatString: "",
Order: "1"
},
{
Title: "Transaction ID",
ExtendedPropertyName: "Id",
ExtendedPropertySource: "Transaction",
FormatString: "{0:G}",
Order: "2"
}
]
}
]
},
{
Name: "CheckImages", /* The name of the tab. Do not change: The code will use this name to reference a tab*/
Title: "Check Images", /*The title is the label or display value for the tab*/
AccountTypeClassFilter: "*", /* The asterisks (*) indicates the tab applies to all account types */
Sections :[] /* Sections containing columns within a tab */
}
]
'

IF (@FOUND = 0)
--CREATE WIDGET SETTING
BEGIN
INSERT INTO CORE.WidgetSetting
(
WidgetID,
Name,
Value,
CreateDate
)
VALUES
(
@WidgetId,
@WidgetSettingName,
@WidgetSettingValue,
GETDATE()
)
END
ELSE
--UPDATE WIDGET SETTING
BEGIN
UPDATE CORE.WidgetSetting
SET
Name= @WidgetSettingName,
Value= @WidgetSettingValue,
CreateDate = GETDATE()
WHERE
Name = @WidgetSettingName AND
WidgetID = @WidgetId
END
SELECT * FROM CORE.WidgetSetting WHERE WidgetID = @WidgetId AND Name = @WidgetSettingName
```

### Alkami Generic Check Imaging Provider

This component allows the legacy system to communicate with the check imaging proxy microservice. This must be installed and configured so that check image requests are properly routed to the new microservice architecture.

```
choco upgrade Alkami.App.Providers.CheckImaging.Generic -y
```

After the upgrade, execute this script to register this component in the core.Provider table.

```
IF NOT EXISTS (SELECT NAME FROM CORE.Provider WHERE AssemblyInfo = 'Alkami.App.Providers.CheckImaging.Generic.Provider, Alkami.App.Providers.CheckImaging.Generic')
BEGIN
insert into core.Provider(ProviderTypeID, Name, Description, AssemblyInfo, CreateDate)
values(10, 'Generic','Connect to the Check Imaging Proxy Microservice', 'Alkami.App.Providers.CheckImaging.Generic.Provider, Alkami.App.Providers.CheckImaging.Generic', GETUTCDATE())
END
```

### Alkami Check Imaging Proxy Microservice

The request for check images happens between a widget and the proxy microservice. This middle layer reduces the amount of change necessary when adding new check imaging providers.

Logical Microservice

There is not a database component for this service. It's a logical service that uses the same request and response objects as a custom check imaging provider.

```
choco upgrade Alkami.MS.CheckImagingProxy.Service.Host -y
```

## Environment Testing

Now that the base components have been installed, we can test the feature.

### Restart IIS and Alkami Services

To make sure everything is talking with each other, it's best to shut down the environment and bring it back up. Use Alkami's PowerShell commandlet.

```
# Stop IIS and Alkami Microservices
Stop-IISAndServices

# Start IIS and Alkami Microservices
Start-IISAndServices
```

### Test the Proxy and Static services

After the services are back up and running, we'll want to test the Check Imaging Proxy and the Static Check Imaging Provider communication. The static provider will return a front and back image for any transaction.

Check Imaging Transaction Filter

```
The static service will return data as long as we have a filter with at least one value. Sending a request without a filter will results in a failed validation of the request object.
```

#### Send the request
- Use the tester to locate the ICheckImagingProxyContract in the panel and double-click the GetCheckImages contract method name.
- After they load, in the center panel select the Filter input field and add a long value of any type to the list.
- Click OK and send the request. The response will contain check imaging information returned by the static provider.
#### Look at the data response

The item list returned has a response for each transaction identifier requested. Each item has a front, back and URI - each representing a stock image no matter what transaction identifier is requested. The transaction identifier and the provider name are included in the item response.

Validations

You can see the following warning validations:

- A missing validator on the Filter object, something a developer should choose to implement in their service implementation.
- An instantiation of an empty sorter, which is an optional member of the request.

### Widget and Generic Provider Testing

After verifying the proxy to static provider communication, it's time to check the end-to-end functionality by logging in and opening a transaction with an associated image.

#### Check Image Transactions

We can look in the database's [core.Transaction] table for an entry with a non-null check image number. This is helpful when testing from the UI. We'll know more details about the transaction and be able to search for them by description.

```
select * from core.Transactions where CheckNumber is not null
```

All these contain the word draft in the description. We'll use this to search in the Accounts widget.

#### End to End Testing - Accounts Widget

Open the browser and authenticate as carol.brady or any other applicable user that has check related transactions.

##### Search for checks

Go to the Accounts widget and in the transaction Search box enter draft to filter for our check related transactions.

##### View Transaction Details

Click a transaction and a dialog opens with an image of the same check seen in the beginning of this guide.

Congratulations. The end-to-end check imaging infrastructure is in place!

## Create a Check Imaging Provider

Prerequisites

Samples and Tutorials (https://confluence.alkami.com/sdk/samples-and-tutorials-62701693.html)

You must have completed the My First Provider Microservice (https://confluence.alkami.com/sdk/my-first-provider-service-67617391.html) tutorial. This section does not detail naming, architecture, provider settings, or provider configuration.

### Visual Studio Template

The final part of this guide is to create a brand new check imaging microservice provider from Alkami's Visual Studio template. This new provider will replace the static check imaging microservice we configured previously (number five in the diagram) or can run along side it.

```
choco upgrade Alkami.SDK.Templates -y
```

### Setup
#### Provider Configuration

Locate the insert_provider_setting.sql in the Service.Host project and run that script against your target database.

Provider Type

It's important to remember we'll be creating a new provider that already has an existing Provider Type. When configuring, we'll want to make sure our new provider is associated with the proper CheckImaging provider type. Leave these values as is in the insert_provider_setting.sql script.

#### Run The Service

After the SQL component is run, build the solution and Run the service.

### Provider Settings

After the service is running, go to Alkami's admin portal and load the integration settings for all Check Imaging providers.

You should see the following providers:

- Generic configured to connect the legacy Bank Service to the new check imaging proxy service
- Static provider that returns stock images for testing
- Our new provider which is a real implementation

#### Update Our Settings

Click Edit on the custom provider. Each of these settings are optional and can be used if needed by your implementation. Give proper descriptions to the final settings. Remove unused definitions from the service. Remove any settings not being used.

It's almost a guarantee there will be a BASEURL setting and some authentication mechanism against that base URL.

In the template RequesterID (RQSTRID), InstitutionId, and CUID are ways that we can identify ourselves to a third-party imaging vendor. Sometimes a preferred image type is passed to the vendor so they can return the data with proper expected extension or passed to a widget so the image can be properly rendered.

### Test the Custom Service

The basic implementation from the template does not require any of the settings to have real actionable items. Those can be filled in later when needed or removed altogether. The service should already be running from the previous step, otherwise start your custom service again.

#### Turn Off The Static Check Imaging Microsercive

Open the Services interface and turn off the Alkami MS CheckImaging Static service. This leaves the new custom check imaging provider as the only service available to return data.

#### Microservice Tester

As a test of life, we'll use the Microservice Tester and set a break point in our implementation class.

Similar to the Static Check Imaging provider test previously, send a request to the Check Imaging Proxy Service, filling out the transaction filter with at least a single number.

Check Imaging Proxy

Remember, there is a proxy layer between the web tier and your custom provider. It's possible, and quicker, to test the provider directly, but it's necessary to verify the proxy can connect to the new custom service that has been created.

Restart the proxy service before testing.

We can return images or URLs. The default behavior will return a stock public image URI and two empty check image objects, for the front and back images, respectively.

#### Test In the Browser
##### Update the Bank Setting

Previously, we tested the Static service and saw two stock images returned to the browser. This test will focus on viewing a check image hosted outside the Alkami domain and linked through a URI returned by a check imaging microservice.

To do this, a bank setting must be updated and the user's machine must have access to https://placeholder.com. (https://placeholder.com.)

https://placeholder.com/

Placeholder.com (http://Placeholder.com) is a free image placeholder service for web designers, serving billions and billions of images each year. You can specify image size & format (.GIF, .JPG, .PNG, .WEBP), background color & text color, as well as the text.

In the product guide, it is noted that we can show check images hosted in another domain by providing a URI response to the check image request. If it is preferred to return an image URI, the bank setting set OverrideCheckImagesWithUri to true.

Go to Alkami's admin portal and open the Bank Settings. Search for OverrideCheckImagesWithUri and set that value to true.

If you updated the Bank Setting to override images with a URI, then you will see a link to open an external window in your browser where the check will be viewable.

The placeholder image is viewed in an opened tab in the same browser window.

## Conclusion

The developer must create their custom image provider, but they must also be comfortable troubleshooting and verifying that all the dependent pieces are correctly configured in their SDK.

### Start With The Static Provider

This provider was created to demonstrate and exercise the check imaging feature. If data is not being returned from this static provider, then data will most likely not be returned from your custom provider. Install and configure this service first, before any customization of the environment takes place.

### Binary Images or URI Links

The developer can return binary image data or a link to an externally hosted image. Remember, displaying URI linked images requires an update to the Bank Settings.

### Check Imaging Proxy Microservice

The check imaging architecture uses a proxy microservice to aggregate many potential providers into a single response. While this is useful, not all implementations need to call the proxy. If you are interested in calling a provider directly, you can do so with the understanding you will not have access to data returned by separate providers.

### The Generic Legacy Provider

Strictly a passthrough provider, the existing Alkami widgets using the legacy Bank Service need this component in place when standing up a new check imaging microservice provider. It's responsible for translating the new CheckImageDetail into a legacy CheckImage data type. For this reason, the developer must be comfortable installing and configuring the Generic check imaging provider.
