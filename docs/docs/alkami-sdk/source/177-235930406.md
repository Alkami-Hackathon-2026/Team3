The AlkamiManifest.xml is an XML file intended to define meta data related to a package.

Please note that the version element in this manifest file is the version of the manifest specification, and not the version of your submission package. At the current time, the proper version number is alway 1.0

Empty dependencies

Cannot have empty dependency element
An empty dependencies element like the one below will throw a null reference exception when attempting to process it. Its better to delete the empty element if there are no dependencies.
<dependencies>
</dependencies>

IMPORTANT!

A copy of the manifest file needs to been in the root of the chocolatey package.

You will add a line like this next to the other File elements in your ...Host.nuspec file in the InstallerOverrides folder

- <file src="../AlkamiManifest.xml" target="/" />

Be sure you check the AlkamiManifest.xml that is created by following these instructions. Make sure it has your proper BankIdentifier (if required for your type of submission).

DO NOT WRAP THE BANKIDENTIFIER IN Curly Brackets {} Or Brackets [] or Single '' or Double "" quotes. (Like the examples below)

```
<bankIdentifiers>
<bankIdentifier name="FI Friendly Name">[bank_guid]</bankIdentifier>
</bankIdentifiers>

<bankIdentifiers>
<bankIdentifier name="FI Friendly Name">{bank_guid}</bankIdentifier>
</bankIdentifiers>

<bankIdentifiers>
<bankIdentifier name="FI Friendly Name">"bank_guid"</bankIdentifier>
</bankIdentifiers>

<bankIdentifiers>
<bankIdentifier name="FI Friendly Name">'bank_guid'</bankIdentifier>
</bankIdentifiers>
```

Attention partners/vendors: Please completely remove the <bankIdentifiers></bankIdentifiers> tag.

## Structure of manifest

The manifest is composed of a header segment and a manifest payload. The manifest payload will vary depending on the submission type (Widget, Microservice, Provider...etc). The segment is required regardless of what submission type you have. See Below for structure and fields that are required.

AlkamiManifest.xml basic components

```
<?xml version="1.0" encoding="UTF-8"?>
<packageManifest>
<version>1.0</version>
<general>
<creatorCode>Creator</creatorCode>
<element>Magic</element>
<componentType>Service</componentType>
<dependencies>
<dependency id="package-id" version="nuget-style-versioning" />
</dependencies>
<bankIdentifiers>
<bankIdentifier name="FI Friendly Name">bank guid</bankIdentifier>
</bankIdentifiers>
<releaseManagement>
<alwaysDeploy>false</alwaysDeploy>
</releaseManagement>
</general>
....
....
</packageManifest>
```

#### version [Required]

This is not the XML version or the product version, this is the manifest version. This cannot be modified

#### CreatorCode [Required]

The creator code is typically aligned with an Alkami Jira project key. It has to be anything other than Alkami

#### Element [Required]

This is the package id/name, for systems that don't use the filename as the package id/name.

#### ComponentType [Required]

This is the name that corresponds to the manifest payload defined below. This should be equivalent to your submission type. (Widget, Microservice...etc)

#### Dependencies [Optional, generall recommended]

The dependency entry follows the nuget spec for dependencies (https://docs.microsoft.com/en-us/nuget/reference/nuspec#dependencies-element). Of note, the AlkamiManifest dependency will support nuget version semantics (https://docs.microsoft.com/en-us/nuget/concepts/package-versioning).

Dependencies are typically found in microservice manifests, but may not be required in Widget or other projects. Dependencies are used for contract validation in an environment, and are not used at deploy/install time. These are typically used for validation tasks to ensure that minimum environment recommendations are being maintained.

#### BankIdentifiers [Required]

This is not REQUIRED for Partner Submissions

This is a relevant bank identifier for Alkami Platform SDK Client use to indicate the FI this component belongs to. This helps to ensure that we have delivered the component to relevant environments. If you need these values, please reach out to the SDK Support team for more details.

#### AlwaysDeploy [Optional]

A boolean field to indicate the package should always be deployed regardless of existing configuration. This field defaults to false. In the case that your componentized provider should be deployed regardless of existing configuration, this value should be set to true. Consequently this value should be, more than likely, false. If you believe this value should be true, please consult with your team lead before proceeding.

## Microservices
### Step-by-step guide
#### No existing manifest

If your project does not have an AlkamiManifest.xml at the root of the project, take the following steps:

- Via your preferred command line interface, path to the folder that contains the related csproj of your package (project root).
- Execute the following command to create a new AlkamiManifest.xml. | New-AlkamiManifest -Type Service |
- In Visual Studio, you may have to add an EXISTING FILE to your solution so that it is viewable in Visual Studio, find and select the newly created AlkamiManifest.xml file.
- View the contents of the file. There are a number of elements that cannot be gleaned from the files alone and will require manual updates from you. After your updates, your AlkamiManifest.xml should look similar to the one found in MicroService AlkamiManifest.
#### Existing manifest

If your project already has an existing manifest, ensure the provider node has been added and populated with the appropriate values. After your updates, your AlkamiManifest.xml should look similar to the one found in MicroService AlkamiManifest. Once you are done with modification of your AlkamiManifest, run the Test-AlkamiManifest script detailed at the bottom of this page.

#### Important new nodes
###### packageManifest → serviceManifest → provider

The provider node under serviceManifest provides details at to what provider type and provider name is associated with this microservice when configured. This value should be sourced from your microservice codebase. The values provided here should directly match what used in the call to ProviderBasedService constructor (https://bitbucket.corp.alkami.net/projects/PLAT/repos/alkami.microservices.settings/browse/ProviderBased/Alkami.MicroServices.Settings.ProviderBasedService/ProviderBasedService.cs#29).

For example, if you were creating the AlkamiManifest for the Corelation SkipPayment Provider, you would use "SkipPayment" for the provider type and "Corelation SkipPayment Provider" for the provider name. These values correspond to the provider that implements the ProviderBasedService (source) (https://bitbucket.corp.alkami.net/projects/AS/repos/alkami.microservices.skippaymentproviders/browse/Corelation/Alkami.MicroServices.SkipPaymentProviders.Corelation.Service.Host/DistributedService.cs#12).

MicroService AlkamiManifest

```
<?xml version="1.0"?>
<packageManifest>
<version>1.0</version>
<general>
<creatorCode>Your_Bank_Identifier</creatorCode>
<element>Your_Full_ServiceName</element>
<componentType>Service</componentType>
<bankIdentifiers>
<bankIdentifier name="FI Friendly Name">bank_guid</bankIdentifier>
</bankIdentifiers>
<releaseManagement>
<alwaysDeploy>false</alwaysDeploy>
</releaseManagement>
</general>
<serviceManifest>
<runtime>framework</runtime>
<entryPoint>Your_Full_ServiceName.Host.exe</entryPoint>
<provider>
<providerType>Billpay</providerType>
<providerName>Bill Pay</providerName>
</provider>
</serviceManifest>
</packageManifest>
```

Read this:

- If you have a migrations tag, then it must contain an actual migration (it cannot be empty or only contain commented out tags). More than likely, you can delete the entire migrations tag, up to and including the closing tag for the migrations element.

## Widgets
### Step-by-step guide
#### No existing manifest

If your project does not have an AlkamiManifest.xml at the root of the project, take the following steps:

- Via your preferred command line interface, path to the folder that contains the related csproj of your package (project root).
- Execute the following command to create a new AlkamiManifest.xml. | New-AlkamiManifest -Type Widget |
- In Visual Studio, you may have to add an EXISTING FILE to your solution so that it is viewable in Visual Studio, find and select the newly created AlkamiManifest.xml file.
- View the contents of the file. There are a number of elements that cannot be gleaned from the files alone and will require manual updates from you. After your updates, your AlkamiManifest.xml should look similar to the one found in the Widget AlkamiManifest code block.
#### Existing manifest

If your project already has an existing manifest, ensure the assemblyInfo node has been added and populated with the appropriate values. After your updates, your AlkamiManifest.xml should look similar to the one found below. Once you are done with modification of your AlkamiManifest, run the Test-AlkamiManifest script detailed at the bottom of this page.

#### Important new nodes

The assemblyInfo node under widgetManifest provides details at to what assembly information is associated with this widget when configured. This value should follow the following form: {Assembly name}. This value can be found in the core.Widget table or sourced from the code itself.

Widget AlkamiManifest

```
<?xml version="1.0"?>
<packageManifest>
<version>1.0</version>
<general>
<creatorCode>Your_Bank_Identifier</creatorCode>
<element>Your_Full_WidgetName</element>
<componentType>Widget</componentType>
<bankIdentifiers>
<bankIdentifier name="FI Friendly Name">bank_guid</bankIdentifier>
</bankIdentifiers>
<releaseManagement>
<alwaysDeploy>false</alwaysDeploy>
</releaseManagement>
</general>
<widgetManifest>
<widgetName>Your.Full.WidgetName</widgetName>
<widgetDescription>This is the description of the widget</widgetDescription>
<widgetInstall>Client</widgetInstall>
<areaName>BankIdentifier_WidgetName</areaName>
<assemblyInfo>{Full path of the widget including namespace}</assemblyInfo>
<displaySettings>Desktop</displaySettings>
<iconName></iconName>
</widgetManifest>
</packageManifest>
```

## Validating a Manifest File
- Open powershell as Administrator
- Use the powershell command:

```
Test-AlkamiManifest -f "<Full pack to your AlkamiManifest.xml>"
```
