Note: some of the Alkami nuget packages contain indirect references to .NET Framework 4.8. If you are using Alkami Release 2020.1 or later (should be all of you by now), then you should begin building your projects against Framework 4.8 to avoid build errors.

### For Widget Projects

There are currently the following restrictions on the reference packages that are permitted for Widget project.

As of release 2022.6 you must use these package versions (if you use the package):

SymConnectMuliplexer.Utilities v2.13 requires the addition of Alkami.Microservices.Accounts.Contracts to be included in your project. However make sure that you do not include the Alkami.MicroServices.Accounts.WebApi.Host package in your project.

Newtonsoft.Json - if used, must be version 8.0.3

NHibernate - must be version 3.0.0.4000

NetMQ - Remain on version 3.3.3.4 or earlier (v4.x is not supported yet)

Alkami.MicroServices.Accounts.Contracts and Alkami.MicroServices.Accounts.Service.Client - do NOT use version 2.26.0 (earlier or later is fine)

If you use Alkami.MicroServices.SSOProviders, do not use version 1.5.0. Either use 1.4.0 or something later than 1.5.0 once it has been released.

If you are using the Alkami.MicroServices.SymConnectMultiplexer then read this:

Always use the same version of the Alkami.MicroServices.SymConnectMultiplexer.Client, Alkami.MicroServices.SymConnectMultiplexer.Contracts, and Alkami.MicroServices.SymConnectMultiplexer.Utilities (if avaialble).

Newly released, the set of packages for Alkami.MicroServices.SymConnectMultiplexer version 2.15 works and those DLLs do not have any other special considerations. If you use 2.15, then no need to read the following.

However if you use an older version of these nuget packages and the included DLLs, then there is a dependency on Alkami.MicroServices.Accounts.Data.2.27.dll. Read the message in the following box.

Unfortunately the Alkami.MicroServices.SymConnectMultiplexer.Utilities v2.9 through v2.14 requires Alkami.MicroServices.Accounts.Data.2.27. So if you use the Alkami.MicroServices.SymConnectMultiplexer packages then please add this nuget package to your project
https://feeds.alkamitech.com/feeds/nuget.dev/Alkami.MicroServices.Accounts.Contracts/2.27.0 (https://feeds.alkamitech.com/feeds/nuget.dev/Alkami.MicroServices.Accounts.Contracts/2.27.0)
and add a file line to your .nuspec to get the Alkami.MicroServices.Accounts.Data.2.27.DLL into your chocolatey package.

If you are using Alkami.MS.AccountsOrchestration.Contracts.2.6.dll or Alkami.MS.AccountsOrchestration.Data.Validations.2.6.dll

Then you must use version 2.30 of Alkami.MicroServices.Accounts.Data and include Alkami.MicroServices.Accounts.Data.2.30.dll within the lib folder in your widget package.

### For Microservices Projects

Alkami.Subscriptions.ParticipatingClient - use 3.7.2 or later (do not use 3.7.0 or 3.7.1)

NetMQ - Remain on version 3.3.3.4 or earlier (v4.x is not supported yet)

Alkami.MicroServices.Accounts.Contracts and Alkami.MicroServices.Accounts.Service.Client - do NOT use version 2.26.0 (earlier or later is fine)

Alkami.Test - use version 4.2.0 (do not try to use anything newer right now)

Moq - use version 4.16.1 (do not try to use anything newer right now)

Other than the above limitation, it is recommended that you update to the most recent versions of any packages you are using.

Note: It is critical that you do not pull packages from any sources that are not approved by Alkami. These are the Alkami feeds you should be using:

https://feeds.alkamitech.com/nuget/nuget.dev (https://feeds.alkamitech.com/nuget/nuget.dev)
https://feeds.alkamitech.com/nuget/ThirdParty (https://feeds.alkamitech.com/nuget/ThirdParty)
(refer to Hardware and Software Requirements (/spaces/SDKC/pages/55347103/Hardware+and+Software+Requirements) for instructions on setting them up)

Do NOT pull any packages from nuget.org or from Microsoft Visual Studio Offline Packages.

### Want to learn more and understand why this matters? Read this:

The following might solidify things:
You need all of the assemblies that your widget will use. EXCEPT, you must not include anything that is in the c:\orb\shared folder that does not include a version in the file name. You are allowed to include Alkami or even 3rd party assemblies that do have a version in the file name even if they are in c:\orb\shared because they are actually the exact same file. You see, if there is no version in the file name, then they might be different versions than the ones in c:\orb\shared and can conflict with each other. If they have the version in the file name they will never conflict.

Now, you can get tricked in this way... if you forget to include an assembly (like Alkami.MicroServices.SymConnectMultiplexer.Service.Client.2.14.dll ) your widget might actually still work for a while if some other widget happens to have that exact same version assembly. But if the other widget gets updated to version 2.15 then BOOM. Your widget stops working because it was compiled against 2.14 and that version cannot be found at runtime anymore.

Or, for another example... if you forget to include an assembly (like Alkami.MicroServices.Settings.Data.5.0.dll) your widget might actually still work for a while if that assembly is in the c:\orb\shared folder. But if a new Alkami release is installed, and the new release has version 5.1 then: BOOM. Your widget breaks because your widget assembly or some other dll that your widget includes cannot load because they are looking for version 5.0.

You might be thinking "Let's just use a binding redirect." That could solve some issues. But it creates a whole set of other issues and is not worth getting into.

But as long as we are on the topic... Newtonsoft.Json.dll is worth thinking about. Several widgets use that assembly. There is no version number in the file name and it exists in c:/orb/shared. There is even a binding redirect in the web.config for WebClient. The binding redirect directs use of the dll to version 8.0.0.0 (which is actually 8.0.3). You must NOT include the dll because it does not have a version in the file name, and also because it exists in c:/orb/shared. So far so good. But if you want to use Newtonsoft.Json then you must also compile your widget against 8.0.3. If you upgrade the nuget package in your widget to version 12 or 13 and compile it will not work. There are two reasons that come into play: 1) the way the binding redirect is written it won't help and 2) there is actually a small contract change to something in the the dll which prevents full interchangeability of version 8.0.3 and the later versions.
