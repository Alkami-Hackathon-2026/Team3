## Overview

The Quick Apply widget is a single source for all product acquisition interfaces in Alkami’s platform. You can configure the widget to provide dedicated loan and account creation workflows and other options to launch external application URLs.

End users can use the Quick Apply to directly access pre-populated forms to apply for loans, open accounts, or be redirected to an external URL.

## Quick Apply in the SDK

Developers can use the SDK to write a custom provider to process a member application built using Alkami's Quick Apply member widget and configured by Alkami's Quick Apply administration widget. The SDK developer will create a microservice that handles an action at each step of the workflow.

#### Quick Apply Client Widget

The member will interact with available products using Alkami's Quick Apply client widget. The widget displays all available products from one or more configured microservice providers. The Quick Apply client widget will communicate only with the Quick Apply Microservice and does not require any reference or knowledge of a custom Quick Apply provider.

```
choco upgrade Alkami.Apps.QuickApply
```

This is a client widget and must be added to the database like any other widget.

insert_quickapply_widget.sql

```
use ***DATABASEGOESHERE***

----------------------- WIDGET + FLAVOR -----------------------
IF NOT EXISTS (SELECT ID FROM core.Widget WHERE Name = 'QuickApply')
BEGIN
DECLARE @BankID bigint;
DECLARE @icon varbinary(max) = null;

SELECT @BankID = ID FROM core.Bank;

INSERT INTO core.Widget
(BankID, Name, AssemblyInfo, Salt, Active, IconImage, IconContentType, CanBeRemoved, DisplaySettings, WidgetType, IconName)
VALUES
(@BankID, 'QuickApply', 'Alkami.Client.Widgets.QuickApply', 0, 1, @icon, 'image/png', 1, 3, 0, 'quick-apply');

DECLARE @WidgetID int = SCOPE_IDENTITY();

INSERT INTO core.FlavorWidget (FlavorID, WidgetID, AddedByDefault, FavedByDefault, Ordering)
SELECT DISTINCT f.ID, @WidgetID, 0, 0, MAX(fw.Ordering) + 1
FROM core.Flavor f JOIN core.FlavorWidget fw ON f.ID = fw.FlavorID
WHERE fw.Ordering < 999 GROUP BY f.ID;
END
```

#### Quick Apply Microservice

Alkami's Quick Apply feature can support one or many microservice providers and requires the results of each provider be aggregated into a single response sent back to the web client browser. While each provider is independent of the other, their product offerings are displayed together on screen. The member user will not know which product is managed by which microservice provider. To accomplish this, Alkami has created a Quick Apply microservice that aggregates data from all configured Quick Apply providers.

```
choco upgrade Alkami.MicroServices.QuickApply.Service.Host
```

After installed, execute this SQL query

Quick Apply Microservice Config

```
DECLARE @Debug BIT = 1;
DECLARE @ProviderName VARCHAR(100) = 'Quick Apply Service';

BEGIN TRAN T1

DECLARE @ProviderTypeID BIGINT = (SELECT ID FROM core.ProviderType WHERE Name = 'QuickApply');

IF (@ProviderTypeID IS NOT NULL)
BEGIN
DECLARE @ProviderID BIGINT = (SELECT ID FROM core.Provider WHERE ProviderTypeID = @ProviderTypeID AND [Name] = @ProviderName);

IF (@ProviderID IS NULL)
BEGIN
INSERT INTO core.Provider (ProviderTypeID, Name, Description, AssemblyInfo)
VALUES (@ProviderTypeID, @ProviderName, 'Quick Apply Service', 'Alkami.App.Providers.QuickApply, Alkami.App.Providers.QuickApply');

SET @ProviderID = SCOPE_IDENTITY();
END

DECLARE @ItemID BIGINT = (SELECT ID FROM core.Item WHERE ItemType = 'Connector' AND ParentId = @ProviderID);
IF (@ItemID IS NULL)
BEGIN
INSERT INTO core.Item (ItemType, ParentId, SecondaryId, Name, CreatedUtc, Version, Deleted)
VALUES ('Connector', @ProviderID, (SELECT TOP 1 ID FROM core.Bank), @ProviderName, GETUTCDATE(), '1.0.0.0', 0);

SET @ItemID = SCOPE_IDENTITY();
END
END

IF (@DEBUG = 1)
BEGIN
PRINT('Rollback')
ROLLBACK TRAN T1
END
ELSE
BEGIN
PRINT('Commit')
COMMIT TRAN T1;
END
```

#### Quick Apply Dynamic Provider Microservice

This is Alkami's simple Quick Apply provider. It's a good training device for an SDK developer as you can configure the Dynamic provider along with your SDK provider and model a more relevant production environment.

```
choco upgrade Alkami.MicroServices.QuickApply.Dynamic.Service.Host
```

The dynamic provider has a database component that must be run as well.

insert_dynamic_quickapply_provider.sql

```
DECLARE @ProviderTypeID BIGINT = (SELECT ID FROM core.ProviderType WHERE Name = 'QuickApply')
IF @ProviderTypeID IS NOT NULL
BEGIN
DECLARE @ProviderID BIGINT = (SELECT ID FROM core.Provider WHERE AssemblyInfo = 'Alkami.App.Providers.QuickApply.Dynamic.Provider, Alkami.App.Providers.QuickApply.Dynamic')
IF @ProviderID IS NULL
BEGIN
INSERT INTO core.Provider (ProviderTypeID, Name, Description, AssemblyInfo)
VALUES (@ProviderTypeID, 'Dynamic Quick Apply Provider', 'Dynamic Quick Apply Provider', 'Alkami.App.Providers.QuickApply.Dynamic.Provider, Alkami.App.Providers.QuickApply.Dynamic')
SET @ProviderID = SCOPE_IDENTITY()
END

DECLARE @ItemID BIGINT = (SELECT ID FROM core.Item WHERE ItemType = 'Connector' AND ParentId = @ProviderID)
IF @ItemID IS NULL
BEGIN
INSERT INTO core.Item (ItemType, ParentId, SecondaryId, Name, CreatedUtc, Version, Deleted)
VALUES ('Connector', @ProviderID, (SELECT TOP 1 ID FROM core.Bank), 'Dynamic Quick Apply Provider', GETUTCDATE(), '1.0.0.0', 0)
SET @ItemID = SCOPE_IDENTITY()
END
END
```

#### Service Capabilities

The template code shares many of these same comments. Place a break point at each of these classes to see the full call flow when working with your provider's products.

##### Data

In the Data folder is the typical pattern for provider settings. You can add custom settings for your provider which might be required when you integrate with non-Alkami endpoints. There are no settings configured out-of-the box and none are required.

##### Service Implementation

Similar to all other services, this class is the entry point of this provider's publicly available methods. The class is implementing an Alkami maintained interface named IQuickApplyProviderContract that all Quick Apply providers must implement. The template has designed each service method to encapsulate an internal class that is responsible for executing the business logic.

##### Business Logic

There is a BusinessLogic folder in the service project that contains a list of classes referenced by the service implementation. Some actions are not necessary and can remain as they are, while others might be more applicable to your customization.

###### GetJointOwnerAction

Optional: Return a list of joint owners which the user may select when applying for an application.

###### GetProductsAction

Return a filtered list of products sourced from Alkami's database or from an external source. This method can be customized to include your own rules, external API requests, or any custom logic you might require to build a product list.

###### OpenAccountAction

Executed when the application workflow has been completed and the disclosure accepted. You can apply any rules or decisioning logic necessary to help with the account opening process. The response object contains a Decision property to declare the result as well as the AccountNumber for a reference to the new account and/or ConfirmationNumber for when a new account is not opening immediately so the end user will have a reference for the application submission to your system.

###### StatusAction

Before any actionable request from the member is made, your provider service will regularly be asked its status. This should return true when the service is ready to provide products and process applications. It should return false when it's not able to do so and the products for this provider will not be shown to the member.

###### GetSupportedFieldsAction

It's possible to recommend which fields your Quick Apply provider prefers when building field workflows. Currectly, AllowAllFields is set to true and will all fields to be used. Alkami recommends to leave this as is unless reason determines otherwise.

###### ValidateProductAction

The product identification field is dictated by your core and/or financial institution. When creating new products, users can enter free form text for the ProductID. This might not match what your core expects. Validate this against your core before allowing it to be saved.
