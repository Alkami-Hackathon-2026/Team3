TITLE: How To Rollout a Standard-SSO Implementation For New and Existing SSO Providers to a Client's Production Environment
PARENT: Standard-SSO
UPDATED: 2026-05-06
URL: https://confluence.alkami.com/spaces/SDKC/pages/556889813
-----
This document describes to process on how to roll out Standard SSO implemented provider to replace an existing SSO provider or to roll out a new provider that was implemented through Standard SSO. For new providers that can be implemented using Standard SSO, the label "StandardSSONew" is added to the ticket.

## Required for Migrations and New SSOs

These steps can be done in any order as they are not reliant on each other. However, the must be done prior to testing of the StandardSSO configuration in any environment.

| Step | Description | Responsible Party |
| 1 | Install certificate if applicable. Some SSOs do not utilize certificates so this step will not always be required. For migration efforts to StandardSSO, certificates can be copied from the APP tier to the MIC tier. | SRE Ops |
| 2 | Whitelist the URL. For migration efforts, whitelisting should be copied from the APP tier to the MIC tier. | Network Engineering |
| 3 | Host Entries. For migration efforts, host entries should be copied from the APP tier to the MIC tier. | Network Engineering |
## Existing SSO Providers

This is applicable in the following scenarios:

- There is a BUG ticket for an existing SSO integration which can be fixed by implementing the widget and microservice/legacy provider to Standard SSO. Typically, the dev ticket has a label of "StandardSSOConversion", which is applied to track development tickets for this purpose.
- There is a STORY ticket for an existing SSO integration that is slated as a Phase 2 item where if implemented through Standard SSO, would satisfy the current set of features as well as address the customization being asked in the feature request. These types of tasks are also labeled with "StandardSSOConversion". A recent example of this is DEV-94157 - Getting issue details... STATUS , where the mobile feature for the ORCAS SSO was an out of the box feature for Standard SSO, but would have been a development task if pursued in the existing ORCAS widget.

| Step | Description | Responsible Party |
| 1 | Add the label "StandardSSOConversion" and the Epic DEV-116387 - Getting issue details... STATUS to the DEV ticket. | Product Manager |
| 2 | Create a Downstream Task. Once a DEV Ticket with a Standard SSO implementation has been completed, the way we trigger the process for TI to promote the Standard SSO configuration to Staging and Production for all applicable FIs and remove the existing widget from the packages of said environments is to create a sub-task with a type of Downstream Task.Example: DEV-112282 - Getting issue details... STATUS | Developer |
| 3 | Add the Standard SSO Configuration in the Downstream Task. Within the development ticket, it's possible that only 1 FI was specified for the bug fix or new feature. Considering that there may be other clients already using the SSO provider in Staging and Production and that all our clients have the same code and how we apply customizations for each one is through configuration, we will need to supply the Standard SSO Configuration information within the Downstream task, only for the FI specified in the development ticket. TI will be in charge of looking for all FIs where the existing SSO provider may be used and will create separate tickets for each of these and will apply the appropriate values for each of them based on the sample provided in the downstream task. The Standard SSO configuration must be a ".txt" attachment in the DST task to make it easier for TI's to consume the data.If there is special logic that will need a developer to interpret to set up a configuration, this must be a separate downstream task. | Developer |
| 4 | Create sql script and repurpose Downstream Task to serve as the TI Ticket template. When a new Standard SSO Implementation TI ticket is received from the Development Downstream Task, a new sql script will be created to simplify the script creation for each FI. That existing Downstream Task will also be updated to include this new sql script so that it can be cloned as the Jira template for each FI and both staging and production. Once done creating sql and Jira template, resolve Downstream Task. Each sql script will convert the following areas directing from the legacy widget to the new Standard SSO widget:Any legacy FI specific provider settings. Links to existing legacy widget within the Accounts/Dashboard widget. Among these are below.View TransactionsPay NowQuick Links to the existing widget.Links to the existing SSO within Quick Apply.Links to the existing SSO provider within CMS Marking Links.Mobile links to the existing SSO provider.Any existing site text for the legacy widget.Example: TI-77926 - Getting issue details... STATUS | TI Engineer |
| 5 | Once Staging and Production tickets are created, convert legacy to Standard SSO in those environments. A comparison between the existing widget behavior and the Standard SSO widget behavior must be performed. If there is a difference in the behavior, this must be noted in the ticket and this can be submitted for Product Review to the Product Owner.Configure Standard SSO in the Staging environment in a hidden state in the exact same flavor and userwidget position as legacy widget. This will enable you to test the behavior and troubleshoot as needed without any clients seeing the new widget. The legacy widget will remain untouched.Once Standard SSO is configured to satisfaction, unhide the Standard SSO widget with displaysetting of legacy widget and hide the legacy widget.Leave Staging ticket in information required pending FI sign off. Tag the owner specified in the Conversion Confluence in a comment to notify them that TI is ready for fi sign off.Configure Standard SSO in the Production environment in a hidden state in the exact same flavor and userwidget position as legacy widget. This will enable you to test the behavior and troubleshoot as needed without any clients seeing the new widget. The legacy widget will remain untouched.Move Production ticket to information required pending FI sign off on staging ticket. Do not make Standard SSO visible in production until the FI approves of the Staging configuration. | TI Engineer |
| 6 | After the DST has been completed an entry for the project will be added in Standard SSO Rollout PSO page by the PSO project manager. | PSO Project Manager |
| 7 | Find all FIs that have this integration in Staging and Production and create a list on the Conversion Confluence. Once TI has completed their tasks for the Downstream Task, they will resolve that ticket. Any resolved Downstream Tasks with StandardSSOConversion label will show at the top of the Conversion Confluence. To make sure we apply the Standard SSO conversion to all FIs in Staging and Production, we will need to have a list to refer to to make sure that all our clients have transitioned over to Standard SSO. This list will be crucial to help determine when to sunset the provider and move the code to our archive. | PSO Project Manager |
| 8 | Create a delivery ticket for any questions that TI has for a client if a delivery ticket does not exist. Add to Conversion Confluence. If there are any site text questions or sample users that are needed by a TI Engineer and a delivery ticket does not exist for the Standard SSO conversion for this existing SSO provider for the FI, a new ticket must be created to forward this communication to the client. If there is already a delivery ticket present, where in this may have been the Phase 2 ticket or the Support ticket that the development ticket is addressing, then add the questions from TI in that ticket. | PSO Project Manager |
| 9 | Create 1 ticket for Staging for each FI. Add to Conversion Confluence. In order to track the implementation effort for each FI that uses the provider in the Conversion Confluence, a ticket must be created for staging. The CSA or Project Manager may need to coordinate with the FI regarding what the values for the site text will be. If staging test users are needed, provide on ticket. The different types of test users needing to be tested are the following:RetailBusiness MasterBusiness sub-user | PSO Project Manager |
| 10 | Create 1 ticket for Production for each FI. Add to Conversion Confluence. In order to track the implementation effort for each FI that uses the provider in the Conversion Confluence, a ticket must be created for production. The CSA or Project Manager may need to coordinate with the FI regarding what the values for the site text will be. If production test users are needed, provide on ticket. The different types of test users needing to be tested are the following:RetailBusiness MasterBusiness sub-user | PSO Project Manager |
| 11 | Find out if there are any marketing materials that should be updated to point to the new Standard SSO URL. Add to Staging and Production tickets. For specific types of SSOs like Account Opening, an FI may have a direct link to the existing SSO widget within the Alkami platform. Find out if they have such links in their FIs own website and ask them to replace it with the new URL that directs them to the Standard SSO widget implementation. | PSO Project Manager |
| 12 | Once all FIs have converted to the Standard SSO implementation, a Development task must be created to delete the code from bitbucket. | Product Manager |
| 12 | Create a Release ticket to remove the element from all environments to deprecate the provider. | Product Manager |
| 13 | Remove the elements (widget and provider or microservice) from the Team Release page as these no longer need to be deployed and tracked. | Product Manager |

## New SSO Providers
| Step | Description | Responsible Party |
| 1 | If a contract gap has been evaluated as a Standard SSO implementation, add the label "StandardSSOContract" to the delivery ticket. The purpose of this is so we can track how many of all contract gaps are "Standard SSO", which translates to cost savings and speed to market. | Product Manager/ Business Analyst |
| 2 | Create a Downstream Task. The downstream task must be assigned a fix version of 2020.6. The reason behind this is because Standard SSO is not dependent on ORB versions and only requires the platform to have at least 2020.6 or a higher version. In the downstream task, add the up and down scripts for the Standard SSO configuration. The Standard SSO configuration must be a ".txt" or ".json"attachment in the DST task to make it easier for TI's to consume the data.Example ticket: RAZR Rewards SSO DEV-100629 - Getting issue details... STATUS . The Downstream task is the subtask under this parent ticket which is DEV-112282 - Getting issue details... STATUS . This contains a text file of the json configuration for RAZR. | Developer |
| 3 | Create a SQL template and the JIRA template for the new provider in the TI ticket that clones the Downstream Task. | TI Engineer |
| 4 | Create 1 ticket for Staging and 1 ticket for Production with the JIRA template provided by TI. | Implementing Project Manager |
| 5 | Execute Staging and Production tickets as per client's approval. | TI Engineer |

## Conversion for existing SSO Providers due to changes in parameters

In this scenario, an FI may request Alkami to update the SSO payload due to business requirements. If this is a SSO that could possibly converted to Standard SSO, a conversion to Standard SSO may be the solution here instead of creating a CCR to update the existing Widget/Microservice.

| Steps | Description | Responsible Party |
| 1 | Add a label "StandardSSOResolvedByConversion" to the delivery ticket. | Product Manager or Business Analyst |
| 2 | Create a dev ticket to convert the existing SSO to Standard SSO with the additional updates included. If this can be done using an existing bug or story, link the delivery ticket to the dev ticket and mark the development ticket with the label "StandardSSOConversion" and add the Epic DEV-116387 - Getting issue details... STATUS to the ticket. | Product Manager |
| 3 | Create the Standard SSO configuration and create a Downstream task for applicable FIs. | Developer |
| 4 | Create a SQL template and the JIRA template for the new provider in the TI ticket that clones the Downstream Task. | TI Engineer |
| 5 | Create 1 ticket for Staging and 1 ticket for Production with the JIRA template provided by TI. | Project Manager |
| 6 | Execute Staging and Production tickets as per client's approval. | TI Engineer |
