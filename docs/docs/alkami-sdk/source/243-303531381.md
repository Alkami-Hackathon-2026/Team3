Our end to end tests need to be as maintainable as possible. Test writing responsibilities will be shared between test engineers and developers, which will further emphasize the need for us to stay organized and adhere to a list of best practices.

### Selectors:

This best practice was mentioned in the cypress link. In summary, we don't want the selectors that we use to be dependent on how we implemented our components. They shouldn't be tied to classes, ids, or any attributes that are actually used by html. This prevents us from breaking tests when changing class names or removing unused Ids, and ensures that we aren't adding arbitrary ids or classes that are only used by tests. Instead, we will use the data-cy custom attribute or text to select elements. See the chart below taken from the Cypress Website:

We can leverage Vue custom directives to help us apply these attributes to html elements only when we're running tests. First create a file called testSelectorDirective.js:

testSelectorDirective.ts

```
export default (el: any, binding: any) => {
if (process.env.ALBUS_LOCAL_DEV) {
el.setAttribute('data-cy', binding.value);
}
};
```

Then we can add it to our main vue app file:

Main.ts

```
import TestTags from '../Shared/Directives/TestTags';

Vue.directive('cy-select', TestTags);

new Vue({
store,
el: '#app',
render: (createElement) => {TestMainPage}
});
```

Now when we want to apply it to elements, we use the directive v-cy-select and we can select the element in cypress with cy.get('[data-cy=VALUE]').

Example

```
#Vue Component Template
<iris-quick-action-button
v-cy-select="'create-savings-goal'"
class="float-right"
kind="highEmphasis"/>#Cypress Test
cy.get('[data-cy=create-savings-goal]')
```

Next, we can define a custom command in our cypress support file (tests/e2e/support/commands.js) that only calls 'get' based off of our custom attribute. This lets us get elements off of the page with simply cy.getComponent(VALUE).

commands.js

```
Cypress.Commands.add('getComponent', (value) => {cy.get(`[data-cy=${value}]`)})
```

Another benefit we that get from working with one selector, is that our conversation with test engineers around selecting html elements is a lot less complicated. ### Page Object Model:

Another best practice we'll use to ensure that our code is maintainable is the Page Object Model. This testing design pattern is based on creating a single class that represents every action the user can take on the page, along with assertions and any request intercepts. When we write our tests, we'll only interact with that class.

Let's looks at an example from the Savings Goal feature:

Without the page object model, our test for layout looks like the below code:

Test - Pre Page Object

```
it('render initial layout and form open', () => {
cy.getComponent('savings-piggy').should('be.visible');
cy.getComponent('title').should('contain', "Savings goals");
cy.getComponent('description').should('contain', "Savings goals help you set aside money for the things you want. We can help you stay on track and achieve your goals.")
cy.getComponent('create-goal').should('contain', "Create a savings goal").click();
cy.getComponent('add-goal-form').should('be.visible');
});
```

Now we can build out a Page Object for our Initial Savings Goal page. If we need multiple actions on a single element, we can group them into sub-objects. If you return this from your grouped test functions, you can chain them together in the test. Be aware that we shouldn't be writing complex methods that are a combination of different actions and assertions. It should be clear based off of the method name the exact action that the user is making.

InitialLandingPage.js

```
export default class InitialLandingPage {

static verifyPigLottie() {
cy.getComponent('savings-piggy').should('be.visible');
}

static verifyTitle(expectedText) {
cy.getComponent('title').should('contain', expectedText);
}

static verifyDescription(expectedText) {
cy.getComponent('description').should('contain', expectedText)
}

static CreateGoal = {
verifyText(text) {
cy.getComponent('create-goal').should('contain', text);
return this;
},
click() {
cy.getComponent('create-goal').click;
return this;
}
}
}
```

Our test after using the Page Object:

Test - Post Page Object

```
it('render initial layout and form open', () => {
InitialLandingPage.verifyPigLottie();
InitialLandingPage.verifyTitle("Savings goals");
InitialLandingPage.verifyDescription("Savings goals help you set aside money for the things you want. We can help you stay on track and achieve your goals.");
InitialLandingPage.CreateGoalButton.verifyText("Create a savings goal").click();

AddSavingsGoalFormPage.Form.shouldBeVisible()
});
```

We can now write our test files without needing to know the details of how we are interacting with components. As long as our page object methods are named sensibly and based off of the action, you should be able to read the tests at a glance.

The benefits are even more apparent when we create tests that move across pages and through workflows. For example, the following test opens the 'Add Savings Goal' sheet, fills it out, and then runs some verification tests on the 'Existing Savings Goals' page. We can clearly see when our flow moves on to the next page.

Create Savings Goal

```
it('create savings goal from landing page', () => {
InitialLandingPage.CreateGoal.click();

AddSavingsGoalFormPage.Accounts.verifyNumberOfAccounts(3);
...(Fill out Savings Goal form using AddSavingsGoalFormPage)

AddSavingsGoalFormPage.Form.clickSubmit()

ExistingSavingsGoalsPage.Accounts.verifyNumberOfAccounts(1)

});
```

Now that we have looked at an example, we can explain the benefits and drawbacks.

#### Benefits:
- Maintainability - The cypress code is only included on the page object. Maintaining our tests is as simple as keeping the page object up to date.The test files will not need to be edited unless the functionality of the feature is changed or more cases are added. Any changes to the interface of the web page are added to the page object, which disperses them to all tests that use it.
- Readability - the tests are essentially written in plain English making them more readable and self documenting The tests are a reflection of the AC and readers of the tests do not need to parse through test code to understand what is happening.Simpler code reviews. We won't need pour over lines of cypress code. As long as each action is written correctly in the page object, we can simply read through the test cases to check what we are testing instead of how we are testing it.
- Tests and feature development can be worked on at the same time as long as the test engineer and developer agree on an interface for the page object. When we combine this with the web page interface set up by our custom selectors, we now have two spots in the feature workflow that we can use to split up work between developers and TEs. We can adjust to whichever workflow we want depending on the status of sprint.

Potential Drawbacks:

- More code - Instead of having only test files and our project code, we need will need to create a suite of page objects. This drawback is lessened by the fact that our client app is broken up into widgets. The number of page objects that we need per widget should be minimal. We will also have test engineers and software developers working in tandem to keep them up to date.
