### Purpose

This guide is a client-facing reference for Financial Institutions using StandardSSO Admin in FI Admin to create, edit, test, and manage Standard SSO configurations.

It consolidates the current guidance from the following source pages:

- StandardSSO Admin
- SSO Creation
- Try Now
- View/Edit Configurations
- Standard SSO - Expression Glossary
- Standard SSO - Expression Syntax
### Who this guide is for

This guide is intended for:

- FI administrators managing Standard SSO integrations in FI Admin
- implementation teams configuring a new Standard SSO
- support teams helping review, test, or troubleshoot an existing Standard SSO configuration
### What StandardSSO Admin does

StandardSSO Admin allows users to manage Standard SSO configurations from the FI admin site.

Using StandardSSO Admin, you can:

- view and search existing Standard SSO integrations
- create a new Standard SSO configuration
- edit an existing configuration
- test a configuration with a specific user by using Try Now
- review configuration history

The goal of the admin experience is to support a more self-serve process for configuring Standard SSO integrations.

### Before you begin

Before working in StandardSSO Admin, confirm the following:

- the StandardSSO Admin feature is enabled for your FI
- your admin role includes the StandardSSO Admin permission
- if you plan to use Try Now, your admin role also includes Login As User (Full Access)
- you have the vendor’s implementation requirements ready before you begin creating the SSO
### Access requirements
#### StandardSSO Admin access

Access to StandardSSO Admin is controlled by both:

- an FI-level feature flag
- a user role permission

The feature flag that must be enabled is:

- EnableStandardSSOAdmin under Internal.StandardSSOAdmin

The required user permission is:

- StandardSSO Admin
#### Try Now access

To use Try Now, the admin role must have:

- Login As User (Full Access)

Login As User (View Only) is not sufficient for Try Now.

### StandardSSO Admin overview
#### Landing page

The landing page shows all existing Standard SSO configurations for the FI.

From the landing page, users can:

- view the existing configurations
- see the associated widget name
- see the last modified date, or creation date if the configuration is new
- sort by name, widget, or modification date
- search by name
- open a configuration for editing
- open configuration history
- create a new SSO
### Creating a new Standard SSO

To create a new Standard SSO:

- open the StandardSSO Admin landing page
- click Create SSO
- select a template, or use the default template
- complete all required fields
- click Generate Config
- review the generated configuration
- click Save SSO

The configuration is not saved, and the widget is not created, until you click Save SSO.

#### Template-based creation

StandardSSO Admin supports pre-made templates for many integrations.

Templates typically include:

- common settings that are used repeatedly for that integration type
- additional template-specific fields based on what is usually required for that implementation

All fields in the template flow are required.

#### Default template

Use the default template when you need:

- a basic starting point
- a configuration you can build from manually
- a place to copy your own values into
#### Core creation fields

All templates include these standard settings:

- Provider Name — the name of the SSO configuration
- Widget Name — the name of the associated widget that will be created
- Description — a short internal description of the SSO; this is not shown to the end user
- Display Settings — what platforms the widget will be enabled for; this defaults to all
#### What gets created when you save

Saving a new SSO creates:

- the Standard SSO configuration
- the associated widget
- the related site text

The widget URL is created as:

```
/StandardSso/<Provider Name>
```

Site text is created under the namespace of the widget name.

### Editing an existing configuration

To open an existing configuration:

- go to the landing page
- click Edit for the desired configuration
#### View mode and edit mode

When a configuration opens, it starts in view-only mode.

To make changes:

- toggle the edit mode switch in the upper-right corner
- make your changes
- save the configuration

If you try to leave the page or turn off edit mode without saving, a warning is shown.

#### Recommended editing workflow

For larger changes, the recommended workflow is:

- copy the JSON into a separate editor
- make the updates there
- validate carefully
- paste the updated JSON back into StandardSSO Admin
- save the configuration

Suggested editors from the source documentation:

- VS Code
- Notepad++
- Sublime

It is also recommended to save a local copy of the JSON before making larger changes.

### Common save errors when editing
#### Malformed JSON

The most common save issue is malformed JSON.

A malformed JSON error usually appears as:

- unable to parse configuration

Common causes include:

- missing commas
- extra trailing commas
- missing opening or closing brackets
- mismatched or missing quotation marks
#### Expression syntax errors

Another common save issue is an expression syntax problem.

Example message:

- Syntax error occurred in <location> for the expression: <incorrect expression>

This usually means:

- the expression name does not exist
- the expression name is misspelled
#### Invalid expression usage

Example message:

- Invalid expression occurred in <location> for the expression: <expression>

This usually means:

- the expression is being used incorrectly
- one or more required arguments are missing
- the wrong number of arguments was supplied

Example from the source documentation:

- using Left without both required arguments
#### Other save errors

Because configurations can vary widely, other save errors may also appear.

In those cases:

- use the error message to identify the location of the problem
- review the surrounding configuration carefully
- compare the expression against the syntax and glossary documents

If you receive an unknown error, the source guidance recommends reaching out to your Alkami contact or the Carbon team.

### Testing with Try Now

Try Now allows admins to test a Standard SSO configuration from inside admin.

It is intended to replicate the end-user experience without requiring you to:

- VAU
- give the test user access to the widget first
- make navigation or package changes just to test the integration
#### Opening Try Now

To use Try Now:

- open the configuration
- click Try Now

If your role does not include Login As User (Full Access), the button will be disabled.

#### User selection

The first step in Try Now is selecting a user.

You can search by:

- name
- username

Partial matching is supported.

#### What the user table shows

The user table shows:

- name
- username
- user type, such as business or retail

For business users, it also shows:

- sub-user or master-user information
- entity information
#### User selection errors

After selecting a user, Try Now may show a yellow toast message if the user does not meet the configuration requirements.

Possible messages include:

- User has no accounts eligible for this SSO
- User has no cards eligible for this SSO
- User is missing email
- User has insufficient permissions to access this SSO
- User is missing a user level extended property required for this SSO
#### Account or card selection

If the configuration uses account-level or card-level values, Try Now will prompt you to select an account or card.

This is typically required when the configuration uses expressions such as:

- AccountNumber
- CardNumber

If the configuration uses only user-level values, the account or card selection step is skipped.

The dropdown values shown in Try Now match what the end user would see.

#### SSO initiation behavior

When the launch begins, the display method from the configuration determines how the SSO opens.

Behavior documented for Try Now:

- Inline works as expected
- NewWindow works as expected
- SameWindow is opened in a new window in Try Now so the admin user is not navigated out of FI Admin
#### Common Try Now errors

If Try Now shows a red error, it usually indicates a configuration issue or a StandardSSO service issue.

Common causes listed in the source documentation include:

- invalid configuration
- null values passed into operation expressions
- HTTP service returning a non-success status code, such as 300 or above

Example from the documentation:

```
{{ Left(AddressLine2, 4) }}
```

If AddressLine2 is null, an error can occur.

Recommended approach:

```
{{ Coalesce(AddressLine2, '') }}
```

### Configuration history

StandardSSO Admin includes a history page for each configuration.

The history page shows:

- all changes made since creation
- changes made inside StandardSSO Admin
- changes made outside StandardSSO Admin, such as direct database-related changes referenced by the source documentation

The line labeled INSERTED indicates the original creation of the configuration.

Selecting View Changes shows the configuration before and after a change side by side.

#### Current history limitations

The current documentation also notes:

- a proper diff view is planned for the future
- copying configurations from the history details page is not currently supported due to a read-only Iris text-field issue
- the displayed user information in history may reflect the StandardSSO microservice service account rather than the specific admin user who made the change
### Working with expressions

Expressions are used throughout Standard SSO configurations to insert dynamic values.

Examples include user values, account values, card values, dates, formatting, and helper functions.

### Expression syntax basics
#### Expression delimiters

Expressions use:

```
{{ ... }}
```

There cannot be spacing between the braces themselves.

Valid examples:

```
{{ FirstName }}
{{ FirstName }}, {{ LastName }}
Who is {{ FirstName }}?
```

#### Constants and operations

An expression can be:

- a constant string
- an operation to be evaluated

All expressions ultimately resolve to a string value.

#### Quotes

Expressions can use either:

- single quotes
- double quotes

Examples:

```
{{ 'Single Tick' }}
{{ "Double Tick" }}
```

If a quote character must be escaped inside the same quote style, it is escaped by doubling it.

Example:

```
{{ 'Bob said ''Does that work?''' }}
```

#### Case sensitivity

Expressions are not case-sensitive.

Example:

```
{{ Append('A', 'B') }}
{{ append('A', 'B') }}
```

#### Whitespace

Expressions are whitespace tolerant inside the operation.

Examples:

```
{{Append('A','B')}}
{{ Append ( 'A' , 'B' ) }}
```

#### Numbers

Expressions can include numbers, but the result is still treated as a string.

Example:

```
{{ 12345 }}
```

#### Methods

Expressions can refer to methods by prefixing the method name with @.

Methods are useful when a value is computed once and reused in multiple places.

Example:

```
{{ @hash }}
```

Method names:

- must exist in the configuration
- are case-insensitive
- must be at least one character long
### Common expression examples for implementers

Below are common examples pulled from the glossary that are useful when building or reviewing a configuration.

#### User and identity values

```
{{ FirstName }}
{{ LastName }}
{{ DisplayName }}
{{ Email }}
{{ UserName }}
{{ UserIdentifier }}
{{ UserId }}
```

#### Account values

```
{{ AccountNumber }}
{{ MaskedAccountNumber }}
{{ AccountDisplayName }}
{{ AccountHolder }}
{{ MortgageNumber }}
{{ CoreName }}
```

#### Card values

```
{{ CardNumber }}
{{ CardDescription }}
{{ CardType }}
{{ CardHolderDisplayName }}
```

#### Formatting and helper functions

```
{{ Append('A', 'B', AccountHolder) }}
{{ Coalesce(City, State, 'Unknown') }}
{{ Left('Input', 4) }}
{{ Right('Input', 4) }}
{{ Lower('Input') }}
{{ Upper('Input') }}
{{ Trim('Input') }}
{{ UrlEncode('Input') }}
{{ Replace(CoreName, ':', '') }}
```

#### Dates and time

```
{{ BirthDate('MM-dd-yyyy') }}
{{ FormatDateTime('MM-dd-yyyy') }}
{{ TransactionCreateDate('MM-dd-yyyy') }}
```

#### Security and transformation helpers

```
{{ Base64Encode('A') }}
{{ Base64Decode('A') }}
{{ HexEncode('A') }}
{{ HexDecode('A') }}
{{ Hash('HashName', 'Input') }}
{{ Encrypt('EncryptName', 'Input') }}
{{ DeriveKey('DeriveKeyName', 'Secret', 16, 32) }}
```

#### Services

```
{{ Http('ServiceName') }}
{{ Jwt('ServiceName') }}
{{ Saml('ServiceName') }}
```

### Expression best practices

Based on the syntax and editing guidance, the safest client-facing recommendations are:

- keep expressions as simple as possible
- validate spelling carefully
- use the glossary to confirm the exact expression name
- use Coalesce when a field may be blank or null
- use methods when the same computed value is needed in multiple places
- make larger edits in a separate editor first
### Practical implementation tips
#### Tip 1: Start with a template when possible

If a template exists, use it. It gives you a faster and safer starting point than building from scratch.

#### Tip 2: Save large edits outside the admin screen first

For large JSON updates, make changes in an editor first, then paste the final result back into StandardSSO Admin.

#### Tip 3: Test with representative users

When using Try Now, test with:

- a user who should succeed
- a user who helps validate filters, permissions, or missing data conditions
#### Tip 4: Watch for null-dependent expressions

If an expression transforms a value that may be missing, guard it with Coalesce.

#### Tip 5: Use history after every meaningful change

After an update, review history to confirm the change was saved and to preserve an audit trail.

### Suggested working checklist

Use this checklist when creating or updating a Standard SSO:

- confirm feature flag and permissions
- confirm Try Now access if testing is needed
- identify whether a template exists
- gather vendor-specific values before starting
- create or open the configuration
- generate or update the configuration
- review expressions carefully
- test with Try Now
- fix any user eligibility or expression issues
- save the final configuration
- review configuration history
