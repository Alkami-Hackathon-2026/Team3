Permissions Requirements for Security, IT, and Network Teams

This document describes the machine-level permissions required to install and run the Alkami SDK on a developer workstation. It is intended to be shared directly with the Security, IT, and Network teams responsible for provisioning access on those machines.

### What's being installed

The Alkami SDK is installed via SDK Wizard (also called the Merlin), an Alkami-built installer that stands up a working local copy of the Alkami platform on a developer machine. As part of that install, Merlin will install and configure the following on the developer's machine:

- SQL Server and SQL Server Management Studio (SSMS)
- PostgreSQL
- Alkami Nexus client libraries and configuration (Nexus is Alkami's tenant data connections service; the SDK uses it to resolve tenant and environment connection information rather than relying on locally cloned databases)
- Microsoft Visual Studio
- Chocolatey (Windows package manager)
- 7-Zip
- The Alkami SDK itself: services, packages, templates, and the DeveloperDynamic sandbox database
### Why elevated permissions are required

Merlin requires root-level (true local administrator) access on the target machine. There are two distinct layers, and both must be in place before the install can succeed:

- The user must be able to install SDK Wizard (Merlin) itself. The SDK Wizard is a Windows application and has to be installed before it can do anything else.
- The SDK Wizard must be able to operate freely on the machine. Once installed, wizard installs, modifies, and removes files, folders, Windows services, environment variables, and registry entries as part of standing up each component listed above.

Without both, Merlin will be blocked partway through and the install will fail.

### The "I have admin" trap

The most common failure mode we see in the field: a developer is told they have local admin on the machine and assumes that's sufficient. In practice, corporate machine images often have local admin restricted by Group Policy, MDM, or endpoint protection — so the account looks like an administrator but cannot actually perform the operations Merlin needs. The user sees an installer error; the underlying cause is the permission model on the machine, not the installer.

### What is required from Security, IT, and Network teams

For each developer machine that will run the SDK, the user account performing the install needs:

- True local administrator rights on the machine (not GPO-restricted "admin")
- Ability to install third-party applications (the list above)
- Ability to create, start, stop, and configure Windows services
- Ability to modify the Windows registry and environment variables
- Ability to create, modify, and delete files and folders system-wide
- Outbound network access to the Alkami-hosted hosts listed under Network access below

If endpoint protection (CrowdStrike, SentinelOne, Microsoft Defender for Endpoint, or similar) is enforced on the developer machine, exclusions will likely also be required for the Merlin install path and the components it installs. Real-time protection routinely quarantines installer artifacts mid-run and produces the same symptom as a permissions failure.

### Network access

If your network enforces strict firewall or proxy policies, the following hosts must be reachable from the developer machine. These are used by Merlin for installer updates and by the One-Click SDK Manager for SDK submissions. Please have your IT or Network team add them to your allow-list before the install begins:

```
atl-gen-alk-sdk-prod-installer-us-east-1.s3.amazonaws.com
```

### Why the scope is broad

The SDK install is invasive by design. It is not dropping a library on the machine; it is spinning up a real, working slice of the Alkami platform locally so developers can build and test against it. The permission requirements above reflect what that actually takes and will not shrink meaningfully under review.
