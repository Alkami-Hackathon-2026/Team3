This will cover how to submit your SDK project and what to expect throughout the submission process.

### Before you submit your project

Prior to submitting your project please review your project and make sure it is in compliance with the SDK Submission Standards and Checklist (/spaces/SDKC/pages/62696705/SDK+Submission+Standards+and+Checklist). You will also need to validate that your project conforms to the version limits of the packages listed in Nuget package requirements (what versions are current) (/spaces/SDKC/pages/82794502/Nuget+package+requirements+what+versions+are+current). Note that this page has specific versions that can be different for widgets vs services.

Ensure your naming conventions for your widget or microservice comply with the following naming conventions as outlined in Widget Coding Guidelines (/spaces/SDKC/pages/53743045/Widget+Coding+Guidelines) and Microservice Coding Guidelines (/spaces/SDKC/pages/53743063/Microservice+Coding+Guidelines). You can get your unique identifier by following the instructions in Name Your SDK Projects (/spaces/SDKC/pages/55353106/Name+Your+SDK+Projects).

Note: The naming conventions are slightly different depending on whether you are submitting a Widget, Provider or Microservice. Submissions that do not following this naming convention are subject to fail the code review and will require the development team to re-submit the component after making the necessary changes. Failing to follow these guidelines will result in approval and/or deployment delays. It is recommended to keep the namespace generated from the template in place for your project.

### Submitting your project

Step One: Uploading your packaged project to your dev feed on the ProGet server. Follow the instructions in Add a package to your development feed (/spaces/SDKC/pages/51351561/Add+a+package+to+your+development+feed)

Step Two: Create an SDK Submission ticket in accordance with the instructions in Submit your SDK projects in Jira (/spaces/SDKC/pages/51351566/Submit+your+SDK+projects+in+Jira)

Once the submission ticket is created the SDK teams automation will move the package through several steps and status transitions.

A key step in the automated submission process will cancel submissions for any previous versions of the same submitted package. Our staging environment can only have one version of a specific package deployed so the assumption has to be that submitting a new version of a package makes the previous versions obsolete, even if deployed to stage and currently being tested.

#### Validating the package

The first step of validation happens in the SDK automation service. If the package fails any of the validation rules the service will leave a comment on the submission ticket with the issues that need to be addressed and the submission will be canceled. Please address those issues and resubmit the project, don't forget to bump the version.

The second step of the validation process is a static scan analysis. This scan is done by a Fortify On Demand. The static code analysis will examine the code for potential security exploits and incorrect coding practices that would cause application instability. The submission will not be reviewed to determine if it meets the functional requirements, or even if the submission works. Any issues will be detailed in the ticket for the client to resolve. A document with the scan results will also be attached to the ticket with a summary of all vulnerabilities that were found as well as suggested mitigation steps. Once the issues have resolved, the updated project will begin need to be submitted and go through the process again. If additional issues are found, this process will repeat. Once the submission passes static analysis it will proceed to SDK team code review.

#### SDK Team Code Review

The code review will check for a variety of different issues and they are outlined in SDK Submission Standards and Checklist (/spaces/SDKC/pages/62696705/SDK+Submission+Standards+and+Checklist). This is a second look at the code by at least two members of the SDK team using the same checklist that should have been before submission. If any issues are found comments will be left in a comment on the ticket. The code review requires two SDK team members to approve it for it to move forward in the submission process. There are several types of comments that might be left on a ticket and only the "Needs Work" comments will require an update to the project a new submission.

Understanding code review comments

Most comments will be self explanatory regarding what actions (if any) you must take.

| Phrase | What it means to you |
| Needs work | This comment describes the reason (or one of the reasons) why the submission is being declined. You will need to make changes to your project to address this item before submitting again. |
| Suggestion | Although this item is not sufficient reason for us to decline the submission, you should make changes the next time you rework your project. |
| Tip | What follows is a general comment that might not even be related to your project code. No action on your part is required. |
| Question | The reviewer is curious about something in your project. These questions will not prevent processing your submission, but you should reply to the question by placing a comment on the submission Jira ticket. |

Some examples of these types of comments:

- Needs Work: Your package is missing the widget's dll file.Suggestion: You should use the AugmentRequest extension method that is contained in WebToolkit rather that maintaining your own method.Tip: Do a web search for "razor syntax" and you will find many examples that will help you in building your views.Question: Are you going to need us to open up a firewall port and configure routing to reach your web service?

When a package passes code review the submission ticket will be transitioned to "Waiting for Stage Deployment" and a ticket is created for our Release Management team to deploy the package to stage. Once this transition happens the SDK automation goes on hold for the submission and the Release Management teams automation takes over. A brief overview of the Release Management Process.

After the stage deployment is complete the Release Management teams automation will update the submission ticket and will transition the status to "Waiting for Stage Validation". At this point the SDK automation will go on hold again for the submission waiting for Stage Testing. For continuation of this flow it will be assumed that the submission was marked as "Stage Validation Passed". This will transition the submission into the "Awaiting Configuration" status.

The rest of the submission process is based on the statuses of the submission ticket explained below.

Awaiting Configuration

When the submission is transitioned into the "Awaiting Configuration" status the SDK automation will pick back up and leave two comments on the ticket. One will be internal to inform our PSO team that a configuration change for production might be associated with this submission and another one that will be sent to the reporter on the ticket with some questions to answer about configuration changes between stage and production. These questions need to be answered if there are changes to the configuration. If there are no changes to the configuration or you plan on making then through the admin site please leave a comment stating that is the course of action. Production deployment will not be scheduled until an SDK team member transitions the ticket to "Waiting for Prod Deployment". The team will not do this until there is confirmation of configuration. It is VERY important that you use the sdksupport, @sdksupport, tag in this comment so that the team is aware that you are ready to move forward with the submission.

Waiting for Prod Deployment

Once the ticket has been transitioned to "Waiting for Prod Deployment" the SDK automation process is complete. The deployment and remaining steps are handled by the Release Management teams automation.

### Ongoing Responsibility for Testing and Updates

Your FI is responsible for ongoing testing and maintenance updates to you submitted code.

Important: For each Alkami release update, the financial institution is responsible for re-testing their SDK-developed and submitted widgets and services.

It is recommended that the financial institution:

- Test in their updated SDK environment.Then, test again in staging.Then, test once again in production.

If changes are needed (whether due to a newly discovered anomaly, or due to changes made to the platform by Alkami), the financial institution is responsible for following the normal submission process to submit an update.

The financial institution will not be charged for a submission due to an update caused by an Alkami breaking change.

### Staging Testing
- Once your submission is in the staging environment, you can test your submission in a production-like environment. It is your responsibility to adequately test your submission in the staging environment.
- Once testing is complete the you will need to transition the ticket by selecting Stage Validation Passed or Stage Validation Failed based on the results of the testing.If stage validation passed and you are ready for it to be promoted to production, a pre-prod environment or both you will need to leave a comment on the ticket with that information. Make sure that you use the sdksupport, @sdksupport, tag in your comment so that the team is aware that you are ready to move forward with the submission.If it is not working as expected, depending on the severity of the issue, either open a support ticket, or create a new SDK Submission ticket with the latest version of the submission that fixes the issues. Note: Creating a new SDK Submission ticket restarts the SDK submission process from the start. Marking the submission as Stage Validation Failed will result in the submission being canceled.
### Production Testing
- When your submission is in Package Deployment Finished, make sure your SDK submission is working as expected.
- If it is not working as expected, depending on the severity of the issue, either open a support ticket, or create a new SDK Submission ticket with the latest version of the submission that fixes the issues. Note: Creating a new SDK Submission ticket restarts the SDK submission process from the start.
