### Description

The Event Management Processors project provides the base classes for all processor microServices that are registered with the Event Management MicroService.

### Steps for creating an Event Management Processor MicroService
#### 1. Select your processor type

There are 3 types of triggers that can be used to trigger a processor, Broker Events, Custom Events or Cron Schedules.

##### Broker Events

If you want your processor to do something when a broker event is received then implement the **IEventProcessor** interface. This interface requires you to specify which broker event your processor will listen for.

```
public Events EventType => Events.AddressChanged;
```

##### Custom Events

If you want your processor to be triggered by an event that is not a broker event then you would implement the ICustomEventProcessor. This interface requires you to specify the name of your custom event.

Note: Make sure your custom event is unique. If 2 different processors both register the same customEventType then they would both end up receiving the events. This may be the desired behavior or it may be that they are 2 different types of events that have different meaning.

```
public string CustomEventType => "SampleEvents::MyFirstEvent";
```

Triggering the custom event is achieved by calling the TriggerCustomEventAsync method on the event management service client. For example:

```
var eventData = new Dictionary<string, string>();

eventData.Add("MyFirstDataElement", "Value 1");
eventData.Add(("MyFirstDataElement", "2");
eventData.Add("UserId", userId); //If any processor subscribing to the custom event is using subscriptions then this UserId would be required in the EventData.

var request = new TriggerCustomEventRequest
{
BankIdentifier = MyBankGuid,
CorrelationId = Guid.NewGuid().ToString(),
CustomEventType = "SampleEvents::MyFirstEvent",
EventData = eventData,
UserId = _currentUser.UserId, //The user who is triggering the event. This is NOT the user that will be used to check subscriptions.
UserIdentifier = _currentUser.UserIdentifier //The user who is triggering the event. This is NOT the user that will be used to check subscriptions.
};

var response = await EventingServiceFactory().TriggerCustomEventAsync(request);
```

The EventData property should contain any data you want included in the payload that is sent to the processor. You can put anything you want in there, but typically it would contain accountIds, transactionIds etc that would be used by the processor to look up the entity rather than passing other properties of an account or transaction.
Note: If the processor is dependent on a specific UserId being provided then UserId should be included in EventData rather than relying on the UserId of the baseRequest. The BaseRequest properties are not passed through to processors.

##### Cron Scheduled

If you want your processor to be triggered on a set schedule then you would implement the ICronProcessor interface. This interface requires you to specify the default cron schedule for your processor.

```
public string DefaultCronExpression { get => @"0 0 2 1/1 * ? *";}
```

##### IProcessorType

Each of the 3 types of processor inherit from the IProcessorType interface. This interface requires you to specify the DefaultDisplayName and DefaultDescription for the processor.

```
public string DefaultDisplayName => "My Processor name";
public string DefaultDescription => "My Processor Description";
```

#### 2. Implement other interfaces depending on processor requirements

Instead of having a base class expose virtual or abstract methods that you may or may not need to override, a composition approach has been adopted. With this approach your provider opts in to additional functionality by implementing various interfaces.

##### IIsNotificationProcessor

Notification processors are a category of processor that a user can subscribe to on the Notification tab of the Settings widget.
To configure a processor as a notification processor implement the IIsNotificationProcessor interface.

```
public string DefaultCategory => "MyDefaultCategory";

public string DefaultWidgetCategoryName => "MyWidget";
```

The DefaultCategory determines the default grouping that the processor will be included in in the notifications tab of the settings widget.
The DefaultWidgetCategoryName determines what widget the user needs to have access to in order to subscribe to this processor's notification. If this is left null or empty then it will be available for all users regardless of what widgets they have in their package.

##### IValidateSubscription

Subscribed processors are a category of processors that a user can subscribe to, whether it be from the notifications tab of the settings widget or any future interface that submits requests to the AddOrUpdateSubscriptionsAsync method on the Event Management service. The IValidateSubscription gives an opportunity for a processor to validate that a subscription is valid before it gets saved in the DB.

```
public Task<ValidateSubscriptionResponse> ValidateUserSubscriptionAsync(ValidateSubscriptionRequest request)
{
var result = new ValidateSubscriptionResponse
{
Subscription = request.Subscription
};
if (request.Subscription.UserSubscriptionContacts.Count > 3)
{
//In this instance we have decided that we will reject any subscriptions that have more than 3 contacts.
//This is an example only and not a real validation rule.
result.ValidationResults.Add(new Data.Validations.ValidationResult {
ErrorCode = Data.Validations.ErrorCode.ValidationError,
Field = "UserSubscriptionContacts",
Message = "Can only subscribe up to 3 contacts",
Severity = Data.Validations.Severity.Error });
}
return Task.FromResult(result);
}
```

##### IIsMandatory and IAllowsIsMandatorySetting

Some processors should be triggered even when there is no subscription set up. This may be an event that is not user specific or it may be an event that is related to a user but the user does not have to be subscribed in order for the the action to proceed (e.g. the General Alerts are sent to users regardless of whether they subscribed to them or not).
There are 2 ways to make a processor mandatory. Either implement the IIsMandatory interface or implement the IAllowsIsMandatorySetting.
The IIsMandatory interface will result in the make the processor always being mandatory. The IAllowsIsMandatorySetting will expose a provider setting where an admin can determine for an FI whether the processor should be mandatory or not.

##### IHasExtendedDefinitions

When calling the GetDefinitions method there is a mapping called IncludeExtendedDefintions. When this is set to true the call to GetDefinitions will check if the processor implements IHasExtendedDefinitions and if it does then it will call the GetExtendedDefinition method of the interface. The extended definition allows you to provide the list of user specific Accounts, AccountIs mask, AccountHas mask or CustomObjects.

```
public Task<ExtendedDefinition> GetExtendedDefinition(GetDefinitionRequest request)
{
//This is where you would get accounts/cards/other custom objects that would be specific to the user making the request
return Task.FromResult(new ExtendedDefinition
{
AccountIds = new List<long> { 1234,4568,78945}
});
}
```

##### IDefinitionHasSections

The definition that a processor exposes can optionally include a Sections object. In the case of notification processors used in the settings widget, the sections is used to dynamically build the drawer that slides out and allows a user to select the accounts and thresholds etc that they want to recieve notifications on. If your processor requires sections then add the IDefinitionHasSections interface.

```
public List<Section> Sections => new List<Section>
{
new Section
{
DefaultDescription = "My First Section Description",
DefaultTitle = "My First Section Title",
Columns = new List<Column>()
{
new Column()
{
CanChooseMoreThanOne = true,
DataType = DataType.Account,
DefaultName = "Account"
},
new Column()
{
DataType = DataType.Custom,
CustomDataType = new Dictionary<string, string>(){{"More","More"}, { "NotMore", "NotMore" } , { "NotLess", "NotLess" } , { "Less", "Less" } },
CanChooseMoreThanOne = false,
DefaultName = "Operator"
},
new Column()
{
DefaultName = "Value",
DataType = DataType.Money,
}
}
}
};
```

##### IAdditionalSettings

Because there are some base settings that we want to make sure different types of processors always have, we have sealed the standard trackable object DefaultSettings, SettingDescriptors and ValidateSettings methods. To enable a processor to expose additional settings an IAdditionalSettings interface has been created. If your processor implements this, then the settings declared in the methods it exposes are added to the base methods.

```
public Dictionary<string, string> AdditionalDefaultSettings()
{
var additionalSettings = new Dictionary<string, string>();

additionalSettings.Add(MySpecialSetting, "My Default Setting Value");

return additionalSettings;
}

public List<SettingDescriptor> AdditionalDescriptors()
{
var additionalDescriptors = new List<SettingDescriptor>();

additionalDescriptors.Add(new SettingDescriptor(MySpecialSetting, "Description of my special setting", typeof(string), true, "My Special Setting"));

return additionalDescriptors;
}

public void Validate(SettingDescriptor settingDescriptor, string settingValue, List<ValidationResult> errors, bool isValidated, ref bool performedValidation)
{

switch (settingDescriptor.Name)
{
case MySpecialSetting:
{
if (string.IsNullOrWhiteSpace(settingValue))
{
errors.AddValidationError(MySpecialSetting, "Value is required", SubCode.ValueUnsupported);
}

if (settingValue == "NotAllowed")
{
errors.AddValidationError(MySpecialSetting, "Value can not be 'NotAllowed'", SubCode.ValueUnsupported);
}
performedValidation = true;
break;
}
default:
{
performedValidation = false;
break;
}
}
}

```

##### IHasParentProcessor

Some processors need to share subscriptions so that a change in subscription for 1 processor is reflected in another (or multiple other) processor(s). To achieve this simply implement the IHasParentProcessor interface. This interface requires you to provide the DefaultParentProcessorName that will be used as the parent. This will be used as the default setting that can then be modified in the provider settings admin screen. When the processor registers itself with Event Management the ParentProcessorName will be used to look up the providerId of the processor that will be used to get the child processor's subscriptions. A processor that has a ParentProcessorName set will not be visible in the notification settings widget.

```
public string DefaultParentProcessorName => "My Parent Provider";
```

##### ITimeToLive

In the event you wish your processor to only handle events that have not "aged out", or that are no older than a certain timespan, simply have your processor implement the ITimeToLive interface. Any EventProcessorHostBase-descendant processor implementing ITimeToLive will check the age of an incoming event against the processor's TimeToLiveSeconds item setting. If the event is too old, it will not be processed.

#### 3. Implement InternalExecuteAsync method

There is still one method that all processors must implement, and that is the InternalExecuteAsync method. This method will be called whenever an event is triggered that is either for a mandatory processor or a user has subscribed to the processor.
Note: When an event is received by event management, it checks for any registered processors that handle that event. If it finds any it then checks if the processor is mandatory or if the user the event is for has subscribed to the processor. It does not check any other criteria in the subscription. For instance for account related events it does not check that the user subscription is for the account the event is related to. That logic must be done inside the InternalExecuteAsync method.

```
public override Task<bool> InternalExecuteAsync(DoWorkRequest request)
{
Logger.Info($"Got a job for subscription Id {request.MetaData.UserSubscriptionId}!!");

if (request.MetaData.UserSubscription){
//This is the user the request is for
var userId = request.MetaData.UserSubscription.UserId;

}

return Task.FromResult(true);
}
```
