The purpose of this document is to demonstrate the Alkami guidelines for microservice naming and file structures/layouts. Standardizing our microservices and packages will allow for better deployment, troubleshooting, and coherency.

For purposes of this document we will be demonstrating with two microservices.

The first microservice will be called SampleDemo for the organization Alkami Technology. The organization uses a well-known identifier Alkami. This microservice will have migrations as an example.

The second microservice will be called ToyFair for the organization US Best Financial Institution. The organization uses a well-known identifier USBFI. This microservice will not have migrations

Microservice executable names should be clear and consistent. This document will do the best it can to lay out examples to follow. Abbreviations are not-preferred. The overriding rule is that full names should be less than 64 characters in length where possible. When in doubt, reach out to either the SDK team or the Architecture team.

### How to properly name your microservice

Note: any microservice created before February1, 2019, is considered to be grandfathered in to these requirements and does not need to be refactored. New microservices will be expected to meet these guidelines.

Microservices should be named in this fashion:

```
<well-known identifier>.MS[.Processor].<Component>[.<Purpose>][.<vendor/client>]
```

The typical pattern of [identifier] indicates an optional component in the name.

Note the lack of .Service in the name, as well as the shortening of .MicroService → .MS as a means of keeping path names shorter. More on shorter path names below.

Examples:

- Alkami.MS.AtLogin
- Alkami.MS.UserLookup
- Alkami.MS.CardManagement.SymConnect
- USBFI.MS.BranchManagement.NorthAmerica
- USBFI.MS.CardManagement

Here are some Microsoft documentation to follow as well https://docs.microsoft.com/en-us/nuget/create-packages/creating-a-package#choosing-a-unique-package-identifier-and-setting-the-version-number (https://docs.microsoft.com/en-us/nuget/create-packages/creating-a-package#choosing-a-unique-package-identifier-and-setting-the-version-number)

Microservices should also have a defined, useful display name. Here is an example of how to choose the display name your microservice.

Display name value

```
<well-known identifier> <Component>[ <Purpose>][ <vendor/client>]
```

## Shorter path names

The importance of shorter path names is due to automation causing paths over 260 characters to induce path API errors on Windows. While modern usage of APIs will allow for full-file-length-paths of 32k Unicode characters, many applications are not written to take advantage of this path length and fail after the 260 character limit. You can find more information here: https://docs.microsoft.com/en-us/windows/desktop/fileio/naming-a-file (https://docs.microsoft.com/en-us/windows/desktop/fileio/naming-a-file)

Example of a failing case and directory layout structure:

```
Alkami.MicroServices.CardManagementProviders/Alkami.MicroServices.CardManagementProviders.SymConnect/Alkami.MicroServices.CardManagementProviders.SymConnect.Service.Host/Alkami.MicroServices.CardManagementProviders.SymConnect.Service.Host.csproj
```

This particular microservice is not, in fact, hosted at a location this deep, but is used as an example for clarity of intent. The line above is 246 characters. If the automation framework were to keep the build path at D:\Bamboo\Workspaces\CardManagementProviders you can see that we have far exceeded the 260 character limit at 290 characters. Likewise, similar naming convention guidance will be provided in this document to ensure consistency.

## Solution and projects organization

RootNamespace and AssemblyName must match the csproj names. The csproj name will also be the package id for choco installation.
