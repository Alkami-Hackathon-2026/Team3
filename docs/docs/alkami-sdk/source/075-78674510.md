### Microservice or IIS Multiplexer ?

In the past, the SymConnect ports were managed by an IIS process. During 2019 we began to transition to a new Microservice (Alkami.MicroServices.SymConnectMultiplexer.Service.Host). For a time both the IIS process, and the new service were used, however by the end of 2019 all Alkami stage and prod systems were transitioned to use only the new service. When the provider setting named 'MultiplexerMode' is set to a value of '2' then all of the SymConnect traffic will go through the microservice. We recommend that all SDK environments that are connecting to SymConnect be configured with MultiplexerMode=2 to function the same way.

### Step-by-step guide

- Change the hosts file entry for the SymConnectMultiplexer to use 127.0.0.1 . (This is actually for the IIS Multiplexer process, but go ahead and check just in case you are using the legacy code and don't know it)
- Make sure the proper IP address of the SDK box was used when configuring the PortDriver.cfg file in Symitar. Note: sometimes the SDK box will have the address translated when connecting to Symitar and you need to make sure Symitar is expecting the connection from the correct, possibly NATed, IP address.
- Test connecting to Symitar from the SDK using Telnet. To do this you open telnet, then open a connection to Symitar. For example if the Symitar box is at ip address 10.10.10.1 and port 13222 was a port assigned to the SDK box, you would enter:.Telnet Command ``` open 10.10.10.1 13222 ``` It can be difficult to determine if the TCP connection was successful. If it fails, you will usually see a message about the failure within about 30 seconds. If successful, you will probably not see any indication on the screen. If the connection is successful, then type in "HANDSHAKE" <Enter>. You should receive back "RSHANDSHAKE" (meaning a response to the handshake). (Note: this will not work if the port is configured to use encryption.) If this HANDSHAKE test does not work, there is no need to continue with the following steps until you can get the HANDSHAKE test working.
- Make sure you have the latest versions of the following packages installed:Required Chocolatey Packageschoco upgrade Alkami.App.Providers.Multiplexer.Clientchoco upgrade Alkami.App.Providers.Core.SymConnectchoco upgrade Alkami.MicroServices.SymConnectMultiplexer.Service.HostNote: for some clients there will be a custom version of the Alkami.App.Providers.Core.SymConnect package. Search the choco.dev feed for your name to see if you need a custom package. A custom package might look like this: Alkami.App.Providers.Core.SymConnect.AwesomeCUPlease read and remember: Once you have connected your SDK to SymConnect you will need to update these packages when you upgrade the Alkami.MachineSetup.Features package. It might need to be upgraded every time, but on occasion these packages change and since they are unique to a specific core system (SymConnect in this case), they are not included in the MachineSetup.Features package. If you ever upgrade your SDK and suddenly you cannot login, it might be because you have lost your connection to the core and an upgrade to these packages is required.
- Check all of the provider settings for the SymConnect core provider. It is helpful to login to the stage admin site and export the settings for the provider so you can refer to them. Usually, you will be connecting your SDK to the same SYM on the same Symitar system as the Alkami stage system is connecting to and all of the settings will be the same except the HOSTIPADDRESS, and the SOCKETLIST.
- To assist in troubleshooting you will find various log files containing 'multiplexer' in the name. The requests log should contain the actual SymConnect requests and responses which will be helpful when troubleshooting.

Provider Configuration Notes

The HOSTIPADDRESS must be an actual IP address (and not a DNS name).

The syntax for the SOCKETLIST config value is: [{"PortValues":"port1,port2,port3"],"MachineName":"sdkMachineName"}] where port1, etc. are the integer values of the ports or sockets that were assigned for this SDK to connect to, and sdkMachineName is the windows name for the SDK machine.

If you are using the Multiplexer microservice (in addition to the legacy provider), then you need to assign separate sockets to the microservice. The syntax for the SOCKETLIST config value will look like this: [{"PortValues":"port1,port2,port3"],"MachineName":"sdkMachineName"},{"PortValues":"port4,port5"],"MachineName":"sdkMachineName_MS"}] where port1, etc. are the integer values of the ports or sockets that were assigned for this SDK to connect to, and sdkMachineName is the windows name for the SDK machine. Notice in this case there are two separate entries. One for the machine name for the legacy SymConnect provider, and one with a suffix "_MS" added to indicate it is for the microservice on that machine.

As of January 2020, we are not using the legacy SymConnection provider anymore. Just set the MultiplexerMode to 2, and only set ports for the multiplexer. Here's an example

[{"MachineName":"sdkmachinename_MS","PortValues":[12100,12101]}]

This is what the entries look like in the Symitar Episys portdriver.cfg file

; for each socket you need to add a line to map the socket to the correct SYM

socket12100 -NET=4 -CRYPT=0 -TIMEOUT=0 -SYC 099

; also need to add an entry to set the source IP address for each socket

12100 192.168.0.10 unknown Alkami SDK Box

Once SDK user had a problem after restarting their machine and found they were getting the following error in the Multiplexer log file "System.Management.Instrumentation.InstanceNotFoundException: Could not find a compatible service for Alkami.MicroServices.Settings.Contracts.ISettingsServiceContract with minimum version of [4.0.0.0]." We are not sure what is causing this problem in this machine, however the following resolved the issue:

- Stopped the Settings microservice
- Stop the Multiplexer microservice
- Start the Settings microservice and wait about 30 seconds.
- Start the Multiplexer microservice and wait about 30 seconds
- It should all be working find now. If you get an error on the first login, try a second time.
- If the problem is recurring after restarting your machine you can try changing the Multiplexer microservice to a startup mode of automatic (delayed start).

Important troubleshooting note: If the SSN for the a user that you previously registered in the SDK is changed in the core, then the user will not be able to login. The Sync will fail and is indicated by an obscure error message in the Alkami.Bank.Host.log " user is not eligible to login for bank" which is accurate but does not give you all the info needed to resolve it. Update the SSN in the core.users table to fix it.
