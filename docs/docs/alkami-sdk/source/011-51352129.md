### Logging in the SDK

All the Alkami services have a namespace that begins with Alkami. The same applies to the SDK developers, except their namespace will begin with their own name that will differ from Alkami. In the following examples, Alkami is used, but you must replace it with your unique name.

### Elevate Logging for WebClient and other C:\Orb Services

All the IIS applications have their own loggers and live in the root folder of their application.

- Use a text editor to open C:\Orb\WebClient\log4net.config. This also applies to any of the other folders under C:\Orb, each will have their own log4net.config
- Locate the Alkami logger and change the value from ERROR (default) to DEBUG. TRACE is also helpful, but noisy.
- If the logger doesn't exist, copy the following one. If it does exist, it should look like this to enable DEBUG log levels.

```
<logger name="Alkami" additivity="false">
<level value="DEBUG" />
<appender-ref ref="StandardRollingFileAppender" />
<appender-ref ref="DebugAppender" />
</logger>
```

### Add A Custom Logger to WebClient

Each logger is designed to capture log messages from a specific namespace. This example uses the namespace USBFI.Client.Widget.MyMoney to create a new logger for the WebClient application.

- Use a text editor to open C:\Orb\WebClient\log4net.config.
- Above or below an existing logger, add the following XML snippet: The existing one will be the Alkami logger.The name of this logger will allow the log4net framework to capture all generated logs coming from any assembly starting with USBFITo be specific and only capture logs from the MyMoney widget, specify the full namespace (USBFI.Client.Widget.MyMoney) in the name field. ``` <logger name="USBFI" additivity="false"> <level value="DEBUG" /> <appender-ref ref="StandardRollingFileAppender" /> <appender-ref ref="DebugAppender" /> </logger> ```

Elevate Logging for Microservices

### Overview

This document explains some best practices for logging in Alkami applications. Application logging is a valuable tool to help identify problems in development and production. If done correctly, and if an infrastructure is in place that allows events to be put into context, it's easier to debug and makes it easier to solve problems sooner. The effective use of logging is critical to supporting an enterprise application like Alkami's that is complex and spread across numerous layers.

### Log Often and Intelligently

Many developers believe there is an inherent performance penalty to logging, so they only try to log extreme conditions such as exceptions. While incorrect logging can be detrimental to an application's performance, if you follow specific patterns and avoid some known issues, millions of lines can be logged to a file with minimal impact to an application. For example, the following simple program can log one million lines in less than 100ms if the logging level is WARN. If you set the logging level to INFO, it still takes less than 10,000ms to log one million lines.

```
using System;
using Alkami.Utilities;
namespace LoggingTest
{
class Program
{
private static readonly ILog Logger = LogManager.GetLogger<Program>();
static void Main(string[] args)
{
DateTime start = DateTime.Now;
Console.WriteLine("Start: {0}", start);
for (int i = 0; i < 1000000; i++)
{
Logger.InfoFormat("This is a test ({0})", i);
}
Console.WriteLine("End: {0}", DateTime.Now);
Console.WriteLine("Elapsed: {0}", DateTime.Now - start);
Console.ReadKey();
}
}
}
```

### Log Levels

You must select the appropriate log level to ensure log entries are classified appropriately to capture valuable information while ignoring the less valuable information until such a time that it becomes important, such as when you must debug a problem. The following describes the logging levels and when it is appropriate to use them. The logging levels are listed from the most critical that occur but least frequent to the least critical but most frequent. For example, FATAL log entries are rare, but if they occur, they are typically logged whereas DEBUG log entries are sprinkled throughout the code and occur frequently but aren't typically important until you must debug an issue.

#### Fatal

The FATAL log level means something went terribly wrong and the application (or at the very least a thread) is about to die horribly. This log entry explains why the application is about to die. These logs should be very infrequent and always investigated.

#### Error

The ERROR log level indicates the application is encountering something unexpected. This isn't a user error (invalid search query) but is an issue such as an assertion failure or network problem. This is typically manifested in the application as an exception. If the error is due to an exception, the complete stack trace should be logged.

Note

There are helper log methods such as ErrorCallStack(string) that log the complete stack trace automatically in Alkami.Utilities. Do not attempt to do this yourself. These logs are more frequent than fatal but should still be infrequent enough that errors are investigated and resolved.
#### Warn

The WARN log level means something occurred that's concerning but not causing the operation to abort. For example, an expected bank setting wasn't found. In this case, the system assumed an appropriate default so that the application could continue but a warning was logged that the setting wasn't found in case the default negatively impacts the application.

#### Info

The INFO log level is the logging level that occurs as a normal operation of the application. INFO log entries are typically logged in the production environment so it should be useful information to trace the state of the application without being too chatty. Ideally, an operator can understand INFO messages and quickly find out what the application is doing. For example, if an application is about to do a transfer, there should be an INFO statement for the transfer saying “[Who] transferred [Amount] from [Where] to [Where]."

#### Debug

The DEBUG log level is typically off in production by default, but enabled when you must gain a greater understanding of what is occurring in the application. Do not be afraid to have Log.Debug() calls littered throughout your code. Log anything that will be useful if you must debug your application strictly on log files. Do not do anything expensive when debug logging unless debug logging has been enabled. For example, if you want to log a complete object graph by deserializing the object, that deserialization should only occur if debug logging is enabled.

#### Trace

The TRACE log level is used for the most detailed level of logging. TRACE is for very low-level and chatty logging statements that can be useful if you want to add very detailed logging to troubleshoot some strange behavior. For example, requests and responses to external systems are a good candidate for the TRACE log level. The TRACE means you are tracing the execution of your application and everything that is occurring and every minute decision is being logged. The distinction between DEBUG and TRACE is the most difficult, but if you put logging statements and plan to remove it after the feature has been developed and tested, it should probably be on TRACE level. That way it can remain in the code but turned on as necessary.

Too much logging

While we definitely want to add logging statements where necessary, too often log statements are being logged at too high a level and make the logs look chatty. A log is chatty when you have to wade through dozens or hundreds of useless logs just to find a useful log. The useful logs should be at INFO or DEBUG. The chatty logs should be at TRACE. Remember, we pay for storage. We typically only log at the INFO level. We don't want a ton of logs at that level but the logs we have should be useful. Be very careful when adding logging to a common library method at a level higher than TRACE. Since that code might be used throughout the application and called numerous times per request, it can generate a huge amount of logging. Instead, library methods should log at the TRACE level show it can be logged when we truly need the additional details.

### Logging Pattern

Every class should follow the following static readonly declaration on the class:

- For non-static classes:static readonly ILog Logger = LogManager.GetLogger<ClassBeingLogged>();
- For static classes:static readonly ILog Logger = LogManager.GetLogger(typeof(ClassBeingLogged));

Loggers should always be readonly.

These declarations ensure the name of the class is associated with the log entry. Having the name of the class allows selective filtering of what to log as well as making the logs much more readable. Within your class, you will log useful information using the appropriate method based on the desired log level.

### Level Log Methods
| Log Level | Method Name |
| TRACE | Logger.Trace() or Logger.TraceFormat() or Logger.LogTrace() |
| DEBUG | Logger.Debug() or Logger.DebugFormat() or Logger.LogDebug() |
| INFO | Logger.Info() or Logger.InfoFormat() or Logger.LogInfo() |
| WARN | Logger.Warn() or Logger.WarnFormat() or Logger.LogWarn() |
| ERROR | Logger.Error() or Logger.ErrorFormat() or Logger.LogError() |
| FATAL | Logger.Fatal() or Logger.FatalFormat() or Logger.LogFatal() |

Note

Rather than using concatenation in the Logger.xxxxx() method you should use formatting with placeholders in the string.

For example, instead of: Logger.Debug("User ID: " + user.ID), use this: Logger.DebugFormat("User ID: {0}", user.ID)

Warning

The format methods do not always play nicely with JSON! The methods, which take a format string, may throw an exception if you pass in a string with curly brackets that are not related to formatting.

Incorrect Example (will throw an exception):

Logger.TraceFormat(jsonString);

Correct Example 1:

Logger.TraceFormat("{0}", jsonString);

Correct Example 2:

Logger.Trace(jsonString);

Be concise and descriptive Each logging statement should contain both data and description. Consider the following examples:

Example 1

Logger.Debug("Message processed");

Logger.Debug(message.getMessageID());

Example 2

Logger.Debug("Message with id '{}' processed", message.getMessageID());

Which log would you like to see while diagnosing failure in an unknown application? I would prefer to see example #2.

Here is another anti-pattern:

```
if(message is TextMessage)
//...
else
Logger.Warn("Unknown message type");
```

Was it so hard to include the actual message type and other useful information in the warning string? I know something went wrong, but what? What was the context? Changing it to the following is much better:

```
if(message is TextMessage)
//...
else
Logger.WarnFormat("Unknown message type. Message ID:[{0}], Type:[{0}]", message.ID, message.GetType());
```

Remember, a log file should be readable, clean and descriptive. Don’t use magic numbers, log values, numbers, ids and include their context. Show the data being processed and show its meaning. Show what the program is actually doing. Good logs can serve as a great documentation of the application code itself.

### Logging Should be Efficient

All log entries need to be very efficient especially if nothing is being logged at that logging level. Remember that the argument list is evaluated before the logging method is called even if logging for that level has been disabled. If an argument to the log method is expensive to obtain, be sure to guard your log statement with a check of the appropriate Logger.IsxxxxxEnabled property or a lambda expression. For example, if you have a Logger.Debug() statement that is logging an object that deserializes an object graph in the ToString() method, the Logger.Debug() method should be either wrapped with an if (Logger.IsDebugEnabled) statement or a lambda expression like shown in the following sections.

### IsxxxxxEnabled Property

The traditional method of only executing a log statement is to check theppropriate property to determine if logging has been enabled for the log level about to be logged. There is a method for each log level as shown in the table below:

#### Level Log Method
| Log Level | Method Name |
| TRACE | Logger.IsTraceEnabled |
| DEBUG | Logger.IsDebugEnabled |
| INFO | Logger.IsInfoEnabled |
| WARN | Logger.IsWarnEnabled |
| ERROR | Logger.IsErrorEnabled |
| FATAL | Logger.IsFatalEnabled |

Here is an example of wrapping a logging method with the appropriate check to see if logging for a particular log level has been enabled:

```
if (Logger.IsDebugEnabled)

Logger.DebugFormat("Data with expensive ToString method = {0}", data.ToString());
```

#### Logger.IsEncryptionEnabled()

There is also a method called Logger.IsEncryptionEnabled(). Make sure to include the parentheses at the end of that method. It is useful for determining when log encryption is off and therefore log entries containing PII need to be sanitized instead of encrypted.

### Lambda Expression

Lambda expressions are the new way to only evaluate method parameters when the log entry is actually being logged. This is the preferred method of logging. Unfortunately, it is only supported in log4net v2.1 (https://www.nuget.org/) and above.

Here is the way to log without a lambda:

```
Logger.DebugFormat("My Class = {0}", myClass);
```

Here is the correct way to log using a lambda:

```
Logger.Debug(m => m("My Class = {0}", myClass));
```

When using a lambda, the parameters such as myClass will only be evaluated when logging for the desired level has been enabled.

### Logging of Personal and Confidential Information

Great care should be taken to not log passwords, tax IDs, credit card numbers, PINs as well as other personal and confidential information. This information should never be logged without masking, redacting or encrypting. How do you do that if the information we are receiving from a core is personal and confidential information? Either mask the personal and sensitive information or encrypt the data. The keys to decrypt the information in staging and production are not generally available to developers. The keys to decrypt are be protected by Security and are only released as necessary to the appropriate operational support representatives.

#### Sanitization and Masking

Sanitization is a pattern within the Alkami application that is useful when you know a particular string contains a value that matches a pattern. Tax IDs, credit card numbers and PINs typically follow this pattern. Passwords are more difficult and need a specialized logging utility to mask the password. We have extension methods that can sanitize strings and ints that contain known patterns of possible confidential information. There are some extension methods in the Alkami.Utilities.Formatting.Utilities.StringUtilities class that can be used to sanitize or mask data:

- SanitizeData()A string extension method that looks for patterns that match credit card numbers, tax IDs or private numbers and masks them if found. The following defines the regular expressions that are used to determine if the data needs to be masked.A credit card is determined based on the following regular expression: ``` "([0-9]{2})" + // first two digits (part of Issuer Identification Number) "(" + "([0-9]{7,13})|" + //all digits "([0-9]{2,2} [0-9]{4,4} [0-9]{4,4} )|" + //spaced quads "([0-9]{2,2}-[0-9]{4,4}-[0-9]{4,4}-)|" + //dashed quads "([0-9]{2,2}-[0-9]{6,6}-[0-9])" + //amex 4-6-5 ")" + "([0-9]{4,4})"); //last four ``` A tax ID is determined based on the following regular expression: ``` \b([0-9]{1,3})([ -]?)([0-9]{2,3})([ -]?)([0-9]{4})([a-zA-Z]?)\b ``` A private number is determined based on the following regular expression: ``` \b(?<![0-9\*\-][:\s]?)([0-9]{2,19})(?![:\s]?[0-9\*\-])\b ```
- MaskCardNumbers()A string extension method that takes a string as input and masks it leaving just the first 2 and last 4 digitsSanitizeData() Example ``` Logger.LogDebug(m => m("SSN: {0}", socialSecurityNumber.SanitizeData())); ```
#### Encryption

Encryption is useful when the contents contain confidential or personally identifiable information (PII) and it isn't reasonable to mask or redact the data. Encryption takes the string, encrypts it with the public key of a certificate and returns an encrypted string that can only be unencrypted using the private key of the certificate. This is most useful in logging. There are several ILog extension methods in the Alkami.Common.LogUtility class as well as in the Alkami.Utilities.LogUtility (https://packagerepo.orb.alkamitech.com/feeds/nuget.dev/Alkami.Utilities) class that can be use to encrypt what is being logged:

- LogInfoEncrypted()An ILog extension method that is comparable to LogInfo() except the message is encrypted before being logged.
- LogWarnEncrypted()An ILog extension method that is comparable to LogWarn() except the message is encrypted before being logged.
- LogErrorEncrypted()An ILog extension method that is comparable to LogError() except the message is encrypted before being logged.
- LogDebugEncrypted()An ILog extension method that is comparable to LogDebug() except the message is encrypted before being logged.
- LogTraceEncrypted()An ILog extension method that is comparable to LogTrace() except the message is encrypted before being logged.

In addition to these ILog extension methods, there are some methods designed to log core request and responses that encrypt the string before logging:

- CreateCoreRequestEntry()Takes a core method name and an XML requestString and logs a CREQ message where the requestString is encrypted.
- CreateCoreResponseEntry()Takes a core method name and an XML responseString and logs a CREQ message where the responseString is encrypted.
- CreateCoreRequestJsonEntry()Takes a core method name and an JSON requestString and logs a CREQ message where the requestString is encrypted.
- CreateCoreResponseJsonEntry()Takes a core method name and an JSON responseString and logs a CREQ message where the responseString is encrypted.

If more flexibility is required for encryption, the Alkami.Utilities (https://packagerepo.orb.alkamitech.com/feeds/nuget.dev/Alkami.Utilities) nuget library contains classes that can encrypt and decrypt using asymmetric encryption. The following static methods are available in the Alkami.Utilities.Cryptography.AsymmetricEncryption class:

- Encrypt(payload, X509 certificate)Encrypt the payload using the given X509 certificate.
- Decrypt(payload)Decrypt the payload. The private key is determined based on the certificate thumbprint that the payload was encrypted with. If the certificate can't be found or the private key is not available, the encryption will fail.

If even more flexibility is required for encryption, the following classes in the Alkami.Utilities (https://packagerepo.orb.alkamitech.com/feeds/nuget.dev/Alkami.Utilities) nuget library can be used:

- Alkami.Utilities.Cryptography.AsymmetricEncryption.Encryptor
- Alkami.Utilities.Cryptography.AsymmetricEncryption.Decryptor

Log encryption can be turned on and off via the app settings. See Alkami.Utilities.Configuration (/pages/viewpage.action?pageId=32246281).

Log Encryption Example

if (Logger.IsTraceEnabled)
{
if (Logger.IsEncryptionEnabled())
{
Logger.LogTraceEncrypted(responseWithPII);
}
else
{

### Log Method Arguments and Return Values

When you find a bug during development, you typically run a debugger trying to track down the potential cause. Now imagine for a moment that you can’t use a debugger. For example, because the bug manifested itself in a production environment a few days ago and all you have is logs. Would you be able to find anything in them? If you follow the simple rule of logging each method input and output (arguments and return values), you don’t even need a debugger any more. Of course, you must be reasonable but every method that: accesses external system (including database), blocks, waits, etc. should be considered. Simply follow the following pattern:

```
public string PrintDocument(Document doc, Mode mode)

{
Logger.TraceFormat("Entering PrintDocument(doc={0}, mode={1})", doc, mode);
String id = DoSomeLengthyOperation();
Logger.TraceFormat("Leaving PrintDocument(): {0}", id);
return id;
}
```

Because you are logging both the beginning and the end of method invocation, you can manually discover inefficient code and even detect possible causes of deadlocks and starvation – simply by looking after “entering” without corresponding “leaving”. If your methods have meaningful names, reading logs would be a pleasure. Also, analyzing what went wrong is much simpler, since on each step you know exactly what has been processed. We could even use a simple AOP aspect to log a wide range of methods in your code. AOP reduces code duplication, but could lead to enormous amount of logs entries. My personal preference is for the developer to log what they believe is useful information.

You should consider DEBUG or TRACE levels as best suited for these types of logs. And if you discover some method are called too often and logging might harm performance, simply decrease logging level for that class or remove the log completely (maybe leaving just one for the whole method invocation?) But it is always better to have too much rather than too few logging statements. Treat logging statements with the same respect as unit tests – your code should be covered with logging routines as it is with unit tests. No part of the system should stay with no logs at all. Remember, sometimes observing logs rolling by is the only way to tell whether your application is working properly or hangs forever.

### Watch Out for External Systems

This is the special case of the previous best practice: if you communicate with an external system, consider logging every piece of data that comes out from your application and gets in. Period. Integration is a tough job and diagnosing problems between two applications (think two different vendors, environments, technology stacks and teams) is particularly hard.

This is a big overhead and if performance is an issue, logging can always be disabled. But what is the point of having a fast, but broken application, that no one can fix or support? Be extra careful when integrating with external systems and prepare to pay that cost. Sometimes the amount of information exchanged with external systems makes it unacceptable to log everything. On the other hand during testing and for a short period of time on production (for example when something wrong is happening), we would like to have everything saved in logs and are ready to pay performance cost. This can be achieved by carefully using logging levels or lambdas. For example, the familiar pattern below can be used to selectively log more when tracing is enabled:

```
Collection<Integer> requestIds = //...
if(Logger.IsTraceEnabled)
Logger.Trace("Processing ids: {0}", requestIds);
else
Logger.Info("Processing ids size: {0}", requestIds.size());
```

If this particular logger is configured to log TRACE messages, it will log the whole requestIds collection contents. But if it is configured to log INFO messages, only the size of collection will be outputted. No check was made for Log.Info because it is assumed a properly configured enterprise logging system is always logging INFO and above.

### Log Exceptions Properly

Logging exceptions is one of the most important roles of logging at all, but many programmers tend to treat logging as a way to handle the exception. They sometimes return a default value (typically null, 0 or empty string) and pretend that nothing has happened. Other times they first log the exception and then wrap it and throw it back:

Logger.ErrorFormat("IO exception {0}", ex);

throw new MyCustomException(ex);

This construct will almost always log the same stack trace two times, because something will eventually catch MyCustomException and log its cause. First of all, avoid logging exceptions, let the framework or container do it for you. Only log the exception if you are handling the exception and capturing the reason for the exception is useful. Log, or wrap and throw back (which is preferable), never both, otherwise your logs will be confusing. For example, if you are calling some service and you expect that service can return a known exception (such as service down) and you have coded to handle that exception, log the exception that you get from the external service with a log description stating something like "XXX service threw an exception. Displayed Service Down Error to user". Include the exception as a parameter to the Logger.Error() method. Conversely, if you aren't handling the exception, do not log the exception. Allow the exception to be thrown from your method and expect the failure to be handled (and logged) at a higher level.

### Avoid Side Effects

Logging statements should have no or little impact on the applications behavior when they are enabled or disabled. For example, if you had a log entry that caused the initialization of a lazy loaded NHibernate collection. When logging is enabled, everything works as expected but when logging was disabled, the collection stopped being initialized causing an application error. Also, you need to make sure your log entries properly handle all argument values including nulls to make sure they don't throw exceptions.

For example, the following log statement would throw an exception if request.getUser() or manager.getPage() or manager.getPage().getUrl() returned null.

Logger.LogTrace(m => m("Id={0} accesses {1}", request.GetUser().getId(), manager.GetPage().GetUrl().toString()))

### Operational Best Practices
#### Log Locally to Files

If you log to a local file, it provides a local buffer and logging isn't blocked if the network or SQL does down. Also, logging locally is extremely fast and doesn't impact SQL Server performance. Log Appenders should allow configuration changes without restarting Typically the logging level in a production system is INFO . That will log informational messages as well as any warnings and errors. When an issue occurs, it is useful to increase the logging level to a much granular level such as DEBUG or TRACE*. The last thing you want to do in production is restart services to change the logging level. The log appender should be configured to watch the configuration file and automatically reload log settings if they change without restarting the application. This allows operations to enable logging to capture additional detail and then set it back to the normal configuration once the information has been captured. Use rotation policies Depending on the logging level, logs can take up tons of space very quickly. This requires setting up a good rotation strategy and policies regarding retention.

Warning

When updating Log4Net levels, be careful to not lower the "root" level logging at "DEBUG" or below, as a bug exists today with NHibernate that will prevent the system from behaving properly. Whenever possible, only update the logging level for the "Alkami" logger.

#### Log Format

The log file should contain at least the following items: date and time down to the millisecond, log level, class name that originated log entry, thread ID, message and any exception stack trace information. Different services must log to different files Since each process keeps the log file opened for writing, each service or process must log to a different log file. Each log file should use a standard logging format string to provide a consistent format across different logs when they are aggregated. Aggregate local logs to a central repository Log files are typically dispersed between numerous repositories across different servers. For example, application log files are split between different services across different servers. If you throw in system logs, event logs, database logs and network logs, operations could spend hours tracking down and correlating the necessary log files. By having a central repository that aggregates and normalizes the logs into a searchable database, log entries across services and tiers can easily be found. Splunk is a commercial product that provides this capability.

### General Principles and Recommendations

Use the Common.Logging not the log4net namespaces. Nothing in your application should refer specifically to log4net . The only exception to this rule is if context sensitive properties want to be logged using the log4net.GlobalContext or log4net.LogicalThreadContext classes. If these are used, they will typically be used at higher levels that set these properties for the context of the request or action.

We should be using Common.Logging 2.1+ to support lambda expressions. Use System.Diagnostics.StopWatch for tracking elapsed time communicating to external interfaces. Log the output of the Elapsed property. Whenever you use a formatted log statement, surround the format argument placeholders (the {}'s) with brackets or parentheses. Doing this will mark the areas in each log message that vary, making reading the log a bit easier. In addition, it makes empty or null formatting arguments or strings with leading or trailing spaces more obvious.

For example, if the following log message was formatted with an empty context.Description value, the message would appear as "Executing task under context []..."

Logger.DebugFormat( "Executing task under context [{0}]...", ( null == context ? "null" : context.Description ) );

Without those brackets, the same message would be written as "Executing task under context ..." The former message makes it obvious that the context failed to provide a description value, the latter does not.

When communicating with an external service, log the request and response using a DEBUG logging level. Logs are part of every story and part of the delivery of a well-written enterprise application. Every developer should review the log output of their application at the highest logging level to make sure the logging is concise, descriptive and useful and something you would be happy to look at if you were asked to debug the application - because more than likely you will be asked to do just that!

All assemblies within the application should be compiled with debugging information with PDBs distributed with the application to enable detailed stack traces that include line numbers.
