Prerequisites

End-to-end testing requires Albus and albus-preset-vue3 and miragejs.

While Component Testing is meant to test a component's functionality, End-to-end Tests (e2e) are UI test cases. We leverage MirageJS and Cypress for mocking services and simulating a user's interactions on a live version of the Widget.

To be clear, it's important to know the difference between E2E and Unit Testing. However, we won't rehash that here. If you'd like to know a bit more about how you test the functionality of an individual component, hop over to the Component Testing section (/spaces/SDKC/pages/303531375/Component+Testing).

## Dependencies

As described in the admonition above, we'll want to make sure we have miragejs, after we've gone through the Vue documentation and added albus-preset-vue3 to our project:

Install Dependencies

```
npm install --save-dev @alkami/orb-layout-mock miragejs
```

## Running E2E Tests

There is a flag in albus substantiate for quickly and easily running E2E tests using Albus

Execute E2E Tests with Albus

```
npx albus substantiate --e2e -C Alkami.Client.Widget.MyWidget
```

Prerequisites

Running tests this way for a VueJS app requires that your vue app is rendered in an element with id "app" - the application will not be rendered if you use anything else.

```
import { createApp } from 'vue';
import App from './App.vue';

void (async () => {
const app = createApp(App);
// ... other app setup

if (process.env.NODE_ENV === 'development' && process.env.ALBUS_LOCAL_DEV === 'cypress') {
const { setup } = await import('./tests/e2e/setup')
await setup();
}

app.mount('#app');
})();

```

With Albus, you can target tests for specific ORB versions and in fact you will be required to specify a version (tip: if you leave it out, it will output which versions are available):

Specify ORB version

```
npx albus substantiate --e2e -C Alkami.Client.Widget.MyWidget --orbVersion 2022.6.0
```

## Testing Multiple Entries

albus-preset-vue3 provides a way to include mulitple new routes to test your multiple entries. By default Albus includes an app.ts entry for both desktop and mobile.

albus.config.js

```
module.exports = {
global: {},
tokens: {
orbWidgetName: 'Example',
clientFolderName: 'WebClient',
areaFolderName: 'Areas'
},
presetConfiguration: {
vue3: {
pluginConfiguration: {
webpack: {
entry: {
app: '<projectNamespace>/Scripts/app.ts',
},
outputPath: {
js: '<projectNamespace>/Scripts',
css: '<projectNamespace>/Styles',
},
autoInject: [
{
chunks: ['app'],
htmlFilePath: '<projectNamespace>/Views/Index.cshtml',
htmlTemplateFilePath: '<projectNamespace>/Views/Index.template.cshtml'
},
{
chunks: ['app'],
htmlFilePath: '<projectNamespace>/Views/Index.cshtml',
htmlTemplateFilePath: '<projectNamespace>/Views/Mobile/Index.template.cshtml'
},
],
routes: [ // Routes created inside the mock environment
{
path: '/', //Route path in the browser
entry: 'app', // What entry to add to the mock
layout: 'desktop', // Which mock layout to use 'desktop', or 'mobile'
},
{
path: '/Mobile/',
entry: 'app',
layout: 'mobile',
},
],
}
}
}
}
}
```

You then should be able to navigate to said path through cypress to test your components in the correct entry.

## How is end-to-end testing structured?

There are three major areas of End-To-End testing that we're going to cover: Scenarios, Test Cases, and Service Mocking. These are dependent aspects and the three together make up the whole of End-To-End testing. In an E2E environment, the engine must render the widget to test within a simulated page.

During this simulation,

- Test Cases attempt to simulate user behavior by interacting with the widget in a pre-defined way.
- Service Mocking comes into play when the widget expects certain pieces of data to be available.
- Scenarios is the orchestration of Test Cases and Service Mocking together.
