### Widget + Microservice Pairing Pattern
## Widget + Microservice Pairing Pattern

Every Alkami SDK integration consists of two independently deployed artifacts that work together: a Client Widget and a Microservice (MS) Host. Understanding this pairing is the foundation of all SDK development.

##### Overview

The widget handles all UI rendering and user interaction inside the Alkami digital banking shell. The microservice handles all backend logic, external API calls, and data transformation. They communicate over HTTP — the widget calls the microservice via a configured endpoint, and the microservice returns data the widget renders.

```
┌─────────────────────────────────────┐
│ Alkami OLB Shell │
│ ┌───────────────────────────────┐ │
│ │ Client.Widget.FeatureName │ │ ← Renders UI, handles user input
│ │ (Razor Views + JS + CSS) │ │
│ └──────────────┬────────────────┘ │
└─────────────────│───────────────────┘
│ HTTP (configured endpoint)
┌─────────────────▼───────────────────┐
│ MS.FeatureName.Service.Host │ ← Business logic, external API calls
│ (ASP.NET Web API) │
└─────────────────────────────────────┘
│
External APIs / Core
```

##### Naming Convention

Both artifacts follow a strict naming convention. Deviating from it will cause deployment failures.

```
# Widget
{ClientCode}.Client.Widget.{FeatureName}

# Microservice
{ClientCode}.MS.{FeatureName}.Service.Host

# Examples
ACME.Client.Widget.SkipAPay
ACME.MS.SkipAPay.Service.Host
```

##### Controller Pattern

Every widget uses a Base + Desktop + Mobile controller split. Put all shared logic in the base; the desktop and mobile controllers only override view-specific behavior.

```
// ACMESkipAPayControllerBase.cs
// Shared logic for both desktop and mobile
public abstract class ACMESkipAPayControllerBase : AlkamiController
{
private readonly ISkipAPayService _skipAPayService;

protected ACMESkipAPayControllerBase(ISkipAPayService skipAPayService)
{
_skipAPayService = skipAPayService;
}

// Shared action — called by both desktop and mobile controllers
protected async Task<ActionResult> IndexCore()
{
var model = new ACMESkipAPayModel
{
EligibleLoans = await _skipAPayService.GetEligibleLoansAsync(CurrentUser.UserId)
};
return View(model);
}

[HttpPost]
protected async Task<JsonResult> SubmitCore(string loanId)
{
var result = await _skipAPayService.SubmitSkipAsync(CurrentUser.UserId, loanId);
return Json(result);
}
}
```

```
// ACMESkipAPayController.cs
// Desktop — delegates to base
public class ACMESkipAPayController : ACMESkipAPayControllerBase
{
public ACMESkipAPayController(ISkipAPayService skipAPayService)
: base(skipAPayService) { }

public async Task<ActionResult> Index() => await IndexCore();

[HttpPost]
public async Task<JsonResult> Submit(string loanId) => await SubmitCore(loanId);
}
```

```
// MobileACMESkipAPayController.cs
// Mobile — same pattern, resolves to Mobile/ views automatically
public class MobileACMESkipAPayController : ACMESkipAPayControllerBase
{
public MobileACMESkipAPayController(ISkipAPayService skipAPayService)
: base(skipAPayService) { }

public async Task<ActionResult> Index() => await IndexCore();

[HttpPost]
public async Task<JsonResult> Submit(string loanId) => await SubmitCore(loanId);
}
```

##### Model Pattern

Keep models simple data containers. Do not put business logic in models.

```
// ACMESkipAPayModel.cs

{
```

##### AlkamiManifest.xml

Every widget must include a manifest that registers it with the Alkami platform. This is how the shell discovers and loads your widget.

```
<?xml version="1.0" encoding="utf-8"?>
<AlkamiManifest>
<Widget>
<!-- Must match your controller name prefix exactly -->
<Name>ACMESkipAPay</Name>
<FriendlyName>Skip A Payment</FriendlyName>
<Description>Allows members to skip a qualifying loan payment.</Description>
<Version>1.0.0</Version>

<!-- The microservice endpoint this widget will call -->
<ServiceEndpoint>https://your-ms-host/api/skipapay</ServiceEndpoint>

<!-- Alkami role required to see this widget -->
<RequiredRole>Member</RequiredRole>

<!-- Desktop and mobile entry points -->
<DesktopController>ACMESkipAPayController</DesktopController>
<MobileController>MobileACMESkipAPayController</MobileController>
</Widget>
</AlkamiManifest>
```

### SSO Integration Pattern Guide
## SSO Integration Pattern Guide

SSO widgets are the most common integration pattern in the SDK. They authenticate the current Alkami user and redirect them to a third-party partner platform without requiring a second login. This pattern is used for insurance portals, wealth management platforms, rewards programs, e-document vendors, and more.

##### How It Works

```
Member clicks widget
│
▼
Widget Controller
- Retrieves current user context from Alkami
- Calls MS.AuthService to generate a signed token/assertion
│
▼
MS.AuthService.Service.Host
- Validates the request
- Builds SAML assertion OR OAuth token
- Signs with partner-provided certificate/secret
- Returns redirect URL with token embedded
│
▼
Widget redirects member to partner URL
│
▼
Partner platform validates token → member is logged in
```

##### Widget Controller

The SSO widget controller is intentionally thin. Its only job is to call the microservice and redirect.

```
// ACMESSOControllerBase.cs
public abstract class ACMESSOControllerBase : AlkamiController
{
private readonly IAuthService _authService;

protected ACMESSOControllerBase(IAuthService authService)
{
_authService = authService;
}

protected async Task<ActionResult> IndexCore()
{
// Build the SSO request from the current Alkami user context
var ssoRequest = new SSORequest
{
UserId = CurrentUser.UserId,
Email = CurrentUser.Email,
FirstName = CurrentUser.FirstName,
LastName = CurrentUser.LastName,
Institution = CurrentUser.InstitutionId
};

// Call the microservice to get the signed redirect URL
var redirectUrl = await _authService.GetSSORedirectUrlAsync(ssoRequest);

if (string.IsNullOrEmpty(redirectUrl))
return View("Error");

return Redirect(redirectUrl);
}
}
```

```
// ACMESSOController.cs
public class ACMESSOController : ACMESSOControllerBase
{
public ACMESSOController(IAuthService authService) : base(authService) { }
public async Task<ActionResult> Index() => await IndexCore();
}

// MobileACMESSOController.cs
public class MobileACMESSOController : ACMESSOControllerBase
{
public MobileACMESSOController(IAuthService authService) : base(authService) { }
public async Task<ActionResult> Index() => await IndexCore();
}
```

##### Microservice: SAML SSO

Use this pattern when the partner requires a SAML 2.0 assertion (most common for enterprise partners like Ameriprise, FIS, Lively).

```
// SSOService.cs in MS.AuthService.Service.Host
public class SamlSSOService : IAuthService
{
private readonly SamlConfig _config;

public SamlSSOService(IOptions<SamlConfig> config)
{
_config = config.Value;
}

public async Task<string> GetSSORedirectUrlAsync(SSORequest request)
{
// Build SAML attribute statements from user context
var attributes = new Dictionary<string, string>
{
{ "email", request.Email },
{ "firstName", request.FirstName },
{ "lastName", request.LastName },
// Add partner-required attributes here
// Do NOT include SSN, account numbers, or raw passwords
};

// Build and sign the SAML assertion
var assertion = SamlBuilder.CreateAssertion(
issuer: _config.Issuer,
audience: _config.Audience,
nameId: request.UserId.ToString(),
attributes: attributes,
certificate: _config.SigningCertificate,
validFor: TimeSpan.FromMinutes(5) // Keep TTL short
);

// Encode and append to the partner's ACS URL
var encodedAssertion = Convert.ToBase64String(
Encoding.UTF8.GetBytes(assertion));

return $"{_config.PartnerAcsUrl}?SAMLResponse={Uri.EscapeDataString(encodedAssertion)}";
}
}
```

```
// appsettings.json (values injected via environment/secrets — never hardcode)
{
"Saml": {
"Issuer": "https://your-institution.alkami.com",
"Audience": "https://partner.example.com/saml/metadata",
"PartnerAcsUrl": "https://partner.example.com/saml/acs",

}

```

##### Microservice: OAuth / Token-Based SSO

Use this pattern when the partner uses OAuth 2.0 or a proprietary JWT-based handoff (common for fintech partners like Narmi, Envoy, AmpliFI).

```
// OAuthSSOService.cs
public class OAuthSSOService : IAuthService
{
private readonly HttpClient _httpClient;
private readonly OAuthConfig _config;

public OAuthSSOService(HttpClient httpClient, IOptions<OAuthConfig> config)
{
_httpClient = httpClient;
_config = config.Value;
}

public async Task<string> GetSSORedirectUrlAsync(SSORequest request)
{
// Exchange user context for a partner access token
var tokenRequest = new FormUrlEncodedContent(new[]
{
new KeyValuePair<string, string>("grant_type", "client_credentials"),
new KeyValuePair<string, string>("client_id", _config.ClientId),
new KeyValuePair<string, string>("client_secret", _config.ClientSecret),
new KeyValuePair<string, string>("user_id", request.UserId.ToString()),
});

var response = await _httpClient.PostAsync(_config.TokenEndpoint, tokenRequest);
response.EnsureSuccessStatusCode();

var tokenResponse = await response.Content.ReadFromJsonAsync<TokenResponse>();

// Return the partner's deep-link URL with the token appended
return $"{_config.PartnerLaunchUrl}?token={tokenResponse.AccessToken}";
}
}
```

##### Security Rules - Non-Negotiable

These apply to every SSO integration regardless of protocol:

```
✅ DO
- Pull user identity exclusively from CurrentUser (Alkami context)
- Store all secrets (certs, client secrets, API keys) in environment variables or a secrets manager
- Set short assertion/token TTLs (5 minutes maximum)
- Validate the partner's redirect domain against an allowlist
- Log SSO initiation events (user ID + timestamp, no PII)

❌ DO NOT
- Pass SSN, full account numbers, card numbers, or passwords in any SSO payload
- Hardcode secrets, certificates, or API keys in source code or appsettings.json
- Trust user-supplied redirect URLs without validation
- Log full SAML assertions or OAuth tokens
- Reuse tokens across sessions
```
